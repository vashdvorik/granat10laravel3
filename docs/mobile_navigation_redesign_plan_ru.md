# План переделки мобильной навигации маркетплейса

Актуализировано: 27.06.2026.

## 1. Контекст

Сейчас публичная мобильная навигация смешивает два сценария:

- покупатель ищет товары, магазины, избранное и каталог;
- продавец входит в кабинет, регистрируется и управляет магазином.

В проекте регистрация всегда означает регистрацию продавца. Покупателю не нужен аккаунт для просмотра каталога, избранного и оформления заказа. Поэтому нижнее мобильное меню публичной части должно быть клиентским, а вход продавца должен быть отдельным и понятным.

Текущие точки входа в коде:

- публичный layout: `resources/views/main_layots.blade.php`;
- нижнее мобильное меню публичной части: `resources/views/main_layots.blade.php`, блок `.mobile-bottom-navbar`;
- layout страниц входа/регистрации: `resources/views/backend/auth/login_layouts.blade.php`;
- форма входа продавца: `resources/views/backend/auth/login.blade.php`;
- форма регистрации продавца: `resources/views/backend/auth/register.blade.php`;
- кабинет продавца: `resources/views/backend/cabinet/layout_cabinet.blade.php`;
- публичные маршруты: `home`, `catalog.index`, `search`, `favorites`, `shops`;
- продавецкие маршруты: `login`, `register`, `account.index`, `account.store.*`, `account.packages.*`.

## 2. Цель

Сделать мобильную навигацию понятной для клиента маркетплейса:

- снизу всегда доступны основные покупательские действия;
- продавец не теряет вход в кабинет;
- регистрация явно называется продавецкой;
- переход из кабинета обратно в маркетплейс заметен;
- меню не смешивает клиентские и продавецкие задачи.

## 3. Целевая структура

### 3.1. Нижнее меню публичной части

Пять пунктов:

1. `Главная` → `home`
2. `Каталог` → `catalog.index`
3. `Поиск` → `search`
4. `Избранное` → `favorites`
5. `Магазины` → `shops`

Убрать из нижнего меню:

- `Кабинет`;
- `Распродажи`.

`Распродажи` остаются доступными через главную, каталог, меню/футер и промо-блоки, но не занимают слот в нижней панели.

### 3.2. Вход продавца в публичной части

В шапке и футере использовать ясные тексты:

- для входа: `Войти продавцу`;
- для регистрации: `Стать продавцом`.

Маршруты не меняются:

- `Войти продавцу` → `route('account.index')` или `route('login')` в зависимости от контекста;
- `Стать продавцом` → `route('register')`.

Если пользователь авторизован, ссылка `Войти продавцу` может вести сразу в `account.index`.

### 3.3. Страницы входа и регистрации

На страницах auth нужно убрать ощущение покупательского профиля:

- заголовок входа: `Войти в кабинет продавца`;
- CTA регистрации: `Стать продавцом`;
- текст под формой: `Нет аккаунта продавца? Стать продавцом`;
- кнопка возврата: `Вернуться в маркетплейс`.

Нижнее меню на auth layout должно повторять клиентскую публичную навигацию:

`Главная`, `Каталог`, `Поиск`, `Избранное`, `Магазины`.

### 3.4. Кабинет продавца

В кабинете продавца сохранить продавецкое меню, но усилить переключение назад:

- пункт `Вернуться в маркетплейс` должен быть видимым на мобильном;
- желательно вынести его в верхнюю область mobile header или закрепить как отдельное действие;
- не добавлять покупательское bottom nav внутрь кабинета продавца, чтобы не смешивать интерфейсы.

## 4. Этапы реализации

### Этап 1. Публичное мобильное меню

Файлы:

- `resources/views/main_layots.blade.php`;
- при необходимости `public/css/style.css`.

Работы:

1. Заменить первый пункт `Кабинет` на `Главная`.
2. Заменить пункт `Распродажи` на `Поиск`.
3. Оставить `Каталог`, `Избранное`, `Магазины`.
4. Настроить активные состояния по текущему route:
   - `home`, `regional.home`;
   - `catalog.index`, `catalog.show`, `regional.catalog.*`;
   - `search`, `regional.search`;
   - `favorites`, `regional.favorites`;
   - `shops`, `seller`, `regional.shops`, `regional.seller`.
5. Проверить, что подписи помещаются на 360px ширине.

Критерий готовности:

- в публичной мобильной панели нет `Кабинет`;
- в публичной мобильной панели нет `Распродажи`;
- покупатель видит `Главная`, `Каталог`, `Поиск`, `Избранное`, `Магазины`.

Тесты:

- обновить/добавить feature-тест публичного layout;
- проверить наличие новых пунктов и отсутствие старых.

### Этап 2. Вход продавца в публичной шапке и футере

Файлы:

- `resources/views/main_layots.blade.php`;
- возможно компоненты footer/header, если будут выделены позже.

Работы:

1. Заменить `Войти в аккаунт` на `Войти продавцу`.
2. Заменить `Зарегистрироваться` в продавецком контексте на `Стать продавцом`.
3. Проверить footer: ссылки `Зарегистрироваться` и `Войти в кабинет` должны быть продавецкими по смыслу.
4. Не добавлять продавецкие ссылки в нижнее клиентское меню.

Критерий готовности:

- продавец видит понятный вход;
- покупательская нижняя панель не содержит продавецких ссылок;
- footer объясняет продавецкий сценарий без термина "аккаунт покупателя".

Тесты:

- feature-тест главной: видны `Войти продавцу` и/или `Стать продавцом`;
- нет `Кабинет` в `.mobile-bottom-navbar`.

### Этап 3. Auth layout для продавцов

Файлы:

- `resources/views/backend/auth/login_layouts.blade.php`;
- `resources/views/backend/auth/login.blade.php`;
- `resources/views/backend/auth/register.blade.php`;
- возможно password views при одинаковом layout.

Работы:

1. Нижнее меню auth layout привести к клиентскому варианту:
   - `Главная`;
   - `Каталог`;
   - `Поиск`;
   - `Избранное`;
   - `Магазины`.
2. На странице входа заменить заголовки и подписи на продавецкий смысл:
   - `Войти в кабинет продавца`;
   - `Нет аккаунта продавца? Стать продавцом`.
3. На странице регистрации заменить общий текст регистрации на:
   - `Стать продавцом`;
   - `Создайте аккаунт продавца`.
4. Сохранить кнопку `Вернуться в маркетплейс`.

Критерий готовности:

- регистрация не выглядит как регистрация покупателя;
- страницы входа/регистрации не ломают клиентскую навигацию;
- пользователь понимает, что создаёт аккаунт продавца.

Тесты:

- feature-тест login/register view;
- проверить тексты `Войти в кабинет продавца`, `Стать продавцом`, `Вернуться в маркетплейс`.

### Этап 4. Переключение из кабинета продавца в маркетплейс

Файлы:

- `resources/views/backend/cabinet/layout_cabinet.blade.php`;
- возможно CSS кабинета: `public/css/cabinet.css` или `cabinet/assets/style.css`.

Работы:

1. Проверить текущий пункт `Вернуться в маркетплейс`.
2. На мобильном сделать его заметным:
   - в верхней панели кабинета;
   - или первым пунктом mobile/sidebar меню;
   - или закреплённой компактной кнопкой.
3. Не добавлять клиентскую нижнюю панель внутрь кабинета продавца.
4. Убедиться, что продавец легко возвращается на витрину после работы с товарами.

Критерий готовности:

- на мобильном в кабинете продавца есть заметный переход в маркетплейс;
- продавецкое меню остаётся продавецким;
- клиентское меню не появляется внутри кабинета.

Тесты:

- feature-тест кабинета: `Вернуться в маркетплейс` присутствует;
- при необходимости визуальная проверка на мобильной ширине.

### Этап 5. Проверка UX и регрессий

Проверить вручную:

1. Главная на 360px, 390px, 430px.
2. Каталог на мобильном.
3. Поиск на мобильном.
4. Избранное на мобильном.
5. Магазины на мобильном.
6. Страница входа продавца.
7. Страница регистрации продавца.
8. Кабинет продавца на мобильном.

Автотесты:

- `php artisan test tests/Feature/HomeControllerTest.php`;
- добавить/обновить тесты layout/auth при реализации;
- при изменении кабинета продавца прогнать релевантные `Backend*` и `Cabinet*` тесты.

### Этап 6. Боковое mobile/hamburger меню

Причина:

- после правки нижней панели у пользователя остаётся второй мобильный вход — hamburger-меню рядом с логотипом;
- этот блок должен быть понятным для покупателя, но при этом давать продавцу явный вход в кабинет.

Файлы:

- `resources/views/main_layots.blade.php`;
- `public/css/style.css`;
- `tests/Feature/HomeControllerTest.php`.

Работы:

1. Добавить заголовок `Меню маркетплейса` и короткое пояснение.
2. Перевести форму поиска на региональный маршрут `search`, чтобы она вела себя как основной поиск.
3. Добавить быстрые покупательские ссылки:
   - `Главная`;
   - `Каталог`;
   - `Магазины`;
   - `Избранное`;
   - `Распродажи`.
4. Оставить дерево категорий отдельной секцией `Категории товаров`.
5. Добавить отдельный блок `Продавцам` с действиями:
   - `Войти продавцу`;
   - `Стать продавцом`.

Критерий готовности:

- hamburger-меню не выглядит как только список категорий;
- покупатель быстро находит основные разделы;
- продавец видит отдельный вход, не смешанный с клиентской нижней панелью;
- региональность поиска и ссылок сохраняется.

### Этап 7. Единый partial для нижнего мобильного меню

Причина:

- нижняя мобильная панель используется минимум в двух местах: публичный layout и auth layout;
- при ручном дублировании эти блоки легко снова разойдутся по ссылкам, подписям или active-состояниям.

Файлы:

- `resources/views/components/mobile-bottom-nav.blade.php`;
- `resources/views/main_layots.blade.php`;
- `resources/views/backend/auth/login_layouts.blade.php`.

Работы:

1. Вынести разметку bottom nav в общий partial `components.mobile-bottom-nav`.
2. В partial сохранить единую структуру:
   - `Главная`;
   - `Каталог`;
   - `Поиск`;
   - `Избранное`;
   - `Магазины`.
3. Поддержать два режима ссылок:
   - с `$regionalUrl` для публичной региональной части;
   - через обычный `route()` для auth layout.
4. Подключить partial в публичном layout и auth layout.

Критерий готовности:

- bottom nav меняется в одном файле;
- публичная часть сохраняет региональные URL;
- auth-страницы сохраняют обычные публичные URL;
- тесты главной и auth-страниц продолжают проверять одинаковый набор пунктов.

### Этап 8. Самодостаточный компонент нижнего мобильного меню

Причина:

- после выноса разметки оставался CSS-дубль: публичная часть держала стили в `public/css/style.css`, auth layout — inline;
- при следующей правке active-состояний или размеров можно было обновить один стиль и забыть второй.

Файлы:

- `resources/views/components/mobile-bottom-nav.blade.php`;
- `resources/views/backend/auth/login_layouts.blade.php`;
- `public/css/style.css`.

Работы:

1. Перенести CSS нижнего мобильного меню в partial `components.mobile-bottom-nav`.
2. Использовать `@once`, чтобы стили не дублировались при повторном подключении компонента.
3. Удалить nav-specific CSS из auth layout.
4. Удалить nav-specific CSS из общего `public/css/style.css`, оставив компонент источником правды.
5. Оставить в auth layout только auth-специфичные правила: скрытие кнопки возврата, размеры header/logo.

Критерий готовности:

- структура и стили bottom nav находятся в одном компоненте;
- публичная главная и auth-страницы продолжают рендерить одинаковое меню;
- в `style.css` и auth layout больше нет копии `.mobile-bottom-navbar`, `.mobile-nav-item`, `.mobile-nav-label`.

### Этап 9. Автономное responsive-поведение bottom nav

Причина:

- auth layout дополнительно управлял видимостью bottom nav через `hidden-md hidden-lg` и JavaScript;
- после выноса компонента это стало лишней связью: layout знал внутренний селектор компонента и вручную менял `display`.

Файлы:

- `resources/views/components/mobile-bottom-nav.blade.php`;
- `resources/views/backend/auth/login_layouts.blade.php`;
- `tests/Feature/SellerEntryNavigationTest.php`.

Работы:

1. Убрать `hidden-md hidden-lg` из корневого элемента bottom nav.
2. В компоненте задать:
   - `display: none` по умолчанию;
   - `display: block` на `max-width: 767px`.
3. Оставить нижний отступ для fixed nav внутри компонента.
4. Удалить из auth layout CSS-правила `hidden-md/hidden-lg`, которые нужны были только для bottom nav.
5. Удалить из auth layout JS, который вручную показывал/скрывал `.mobile-bottom-navbar`.

Критерий готовности:

- компонент сам отвечает за mobile/desktop видимость;
- auth layout не содержит `querySelector('.mobile-bottom-navbar')`;
- bottom nav не зависит от Bootstrap-like helper-классов.

## 5. Не делать в рамках этой задачи

- Не вводить аккаунты покупателей.
- Не добавлять `Мои заказы` в нижнее клиентское меню.
- Не менять бизнес-логику регистрации: регистрация остаётся регистрацией продавца.
- Не переносить маршруты `account.*`.
- Не удалять страницу `sale`; убрать только из нижней мобильной панели.
- Не смешивать публичный bottom nav с меню кабинета продавца.

## 6. Риски

- На auth layout сейчас есть отдельная мобильная панель. Если поменять только публичный layout, страницы входа останутся непоследовательными.
- В проекте есть региональные маршруты. Активные состояния должны учитывать `regional.*`.
- Часть текста в шаблонах уже менялась, поэтому перед правкой нужно смотреть текущий diff и не откатывать чужие изменения.
- Нижняя панель должна помещаться на маленьких экранах без переноса длинных слов.

## 7. Рекомендуемый порядок выполнения

1. Реализовать этап 1 и покрыть тестом.
2. Реализовать этап 2 и проверить публичную главную.
3. Реализовать этап 3 и проверить login/register.
4. Реализовать этап 4 после согласования визуального варианта кабинета.
5. Выполнить ручную мобильную проверку и точечные feature-тесты.
