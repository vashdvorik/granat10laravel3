## 1. Цель

Перевести маркетплейс с единой общей витрины на региональную модель, в которой посетитель выбирает населённый пункт и получает релевантные товары, магазины, поиск, страницы и SEO-контент.

Региональность должна охватывать:

- публичную витрину;
- каталог и категории;
- поиск;
- распродажу;
- магазины и товары;
- кабинет продавца;
- Filament;
- кеширование;
- sitemap, canonical, robots и метаданные;
- аналитику и тестирование.

Внедрение не должно ломать старые URL, существующие товары и работу сайта без выбранного города.

## 2. Основные решения

### 2.1. Источник местоположения товара

Местоположение принадлежит продавцу, а не товару.

Связь:

```text
Region -> Settlement -> Seller -> Product
```

Один магазин имеет основной населённый пункт. Все его товары относятся к этому населённому пункту, пока не появится отдельная бизнес-потребность в нескольких филиалах.

### 2.2. Режим «Все регионы»

Сайт обязан работать без выбранного населённого пункта.

Режим «Все регионы»:

- показывает все доступные товары;
- сохраняет совместимость со старыми URL;
- используется как безопасный fallback;
- не должен автоматически назначать пользователю случайный город.

### 2.3. URL

Целевая схема:

```text
/{location}/catalog
/{location}/catalog/{category}
/{location}/search
/{location}/sale
/{location}/shops
/{location}/shops/{seller}
/{location}/product/{product}
```

Примеры:

```text
/tiraspol/catalog
/bendery/catalog/telefony
/rybnitsa/search?q=ноутбук
```

`location` — уникальный стабильный slug населённого пункта.

Старые URL `/catalog`, `/search`, `/shops`, `/product/...` сохраняются. На первом этапе они обслуживают режим «Все регионы». Автоматический redirect на региональный URL включается только после проверки аналитики и SEO.

### 2.4. Определение региона

Приоритет:

1. slug в URL;
2. явно выбранный пользователем населённый пункт;
3. cookie;
4. session;
5. режим «Все регионы».

IP-геолокация может использоваться только как необязательная подсказка. Нельзя автоматически и незаметно менять регион пользователя по IP.

## 3. Модель данных

### 3.1. Таблица `regions`

Поля:

- `id`;
- `name`;
- `type`;
- `slug`;
- `is_active`;
- `sort_order`;
- `meta_title`;
- `meta_description`;
- timestamps.

Ограничения:

- `slug` уникален;
- активность управляется администратором;
- регион нельзя удалить при наличии населённых пунктов.

### 3.2. Таблица `settlements`

Поля:

- `id`;
- `region_id`;
- `name`;
- `type`;
- `zip`;
- `slug`;
- `is_active`;
- `sort_order`;
- `meta_title`;
- `meta_description`;
- timestamps.

Ограничения:

- внешний ключ на `regions`;
- `slug` уникален глобально;
- населённый пункт нельзя удалить при наличии продавцов;
- индекс по `region_id`, `is_active`, `sort_order`.

### 3.3. Изменение `sellers`

Добавить:

- nullable `settlement_id`;
- индекс и внешний ключ;
- политику удаления `restrict`.

На переходном этапе поле nullable. После назначения местоположения всем рабочим продавцам и проверки production-данных его можно сделать обязательным.

### 3.4. Модели и связи

`Region`:

- `hasMany(Settlement::class)`;
- scopes `active()` и `ordered()`.

`Settlement`:

- `belongsTo(Region::class)`;
- `hasMany(Seller::class)`;
- scopes `active()` и `ordered()`.

`Seller`:

- `belongsTo(Settlement::class)`;
- доступ к региону через `settlement.region`.

`Product`:

- фильтрация по населённому пункту через связь продавца;
- отдельный scope `forSettlement()`.

## 4. Исходные данные

Создать идемпотентный `RegionsAndSettlementsSeeder`.

Сидер должен:

- импортировать предоставленный список регионов и населённых пунктов;
- использовать `updateOrCreate`;
- генерировать стабильные slug;
- не удалять вручную добавленные записи;
- безопасно запускаться повторно;
- сохранять ZIP как строку;
- поддерживать русские названия.

Перед production-запуском проверить:

- официальное написание названий;
- почтовые индексы;
- отсутствие дубликатов;
- выбранные slug;
- соответствие населённых пунктов регионам.

## 5. Миграция существующих продавцов

Нельзя автоматически назначать всем продавцам Тирасполь без подтверждения.

Порядок:

1. добавить nullable `settlement_id`;
2. вывести в Filament список продавцов без местоположения;
3. назначить населённые пункты вручную или импортом;
4. запретить публикацию нового магазина без населённого пункта;
5. проверить, что активные товары имеют продавца с местоположением;
6. после завершения миграции решить, делать ли поле обязательным в БД.

До назначения города товары продавца видны только в режиме «Все регионы».

## 6. Контекст региона в приложении

Создать:

- `RegionalContext`;
- `ResolveRegionalContext` middleware;
- value object или DTO выбранного региона;
- конфигурацию regionality;
- cookie с ограниченным сроком хранения.

`RegionalContext` должен предоставлять:

- текущий населённый пункт;
- текущий регион;
- режим «Все регионы»;
- slug;
- методы построения региональных URL.

Контроллеры и Blade не должны напрямую читать cookie или session.

## 7. Переключатель города

В шапке сайта добавить:

- текущий населённый пункт;
- кнопку «Выбрать город»;
- поиск по населённым пунктам;
- группировку по регионам;
- вариант «Все регионы»;
- подтверждение выбора.

Требования:

- доступность с клавиатуры;
- корректная мобильная версия;
- сохранение выбора;
- переход на эквивалентную региональную страницу;
- отсутствие redirect-loop;
- безопасный fallback, если населённый пункт отключён.

## 8. Региональная фильтрация

Фильтрация должна быть централизована, а не дублироваться в контроллерах.

Создать scopes или query objects:

- `Product::forSettlement()`;
- `Seller::forSettlement()`;
- `ProductSearchQuery`;
- региональный фильтр в `CatalogPageService`.

Регион применяется к:

- главной странице;
- каталогу;
- странице категории;
- поиску;
- распродаже;
- списку магазинов;
- странице магазина;
- избранному;
- AJAX «Загрузить ещё»;
- счётчикам товаров категорий;
- рекомендациям и похожим товарам;
- sitemap.

Правило товара:

```text
товар активен
+ продавец имеет активный тариф
+ продавец относится к выбранному населённому пункту
```

В режиме «Все регионы» региональный фильтр не применяется.

## 9. Кеширование

Все кеши, зависящие от выдачи, должны включать региональный ключ.

Пример:

```text
catalog:{settlement|all}:{filters}
category-count:{settlement|all}:{category}
sellers:{settlement|all}
search:{settlement|all}:{query}:{filters}
```

Нужно изменить:

- `CatalogCacheService`;
- observer товаров;
- observer продавцов;
- observer подписок;
- прогрев категорий;
- кеш корневого меню, если количество товаров влияет на отображение.

Критический тест: пользователь одного города не получает кешированную выдачу другого города.

## 10. Поиск

Регион становится обязательным фильтром поискового слоя.

Текущая MySQL-реализация:

- фильтрует через продавца и `settlement_id`;
- сохраняет режим «Все регионы»;
- включает регион в пагинацию и AJAX URL.

При внедрении Scout/Meilisearch в поисковый документ добавить:

- `settlement_id`;
- `settlement_slug`;
- `region_id`;
- `region_slug`;
- `seller_id`;
- признак доступности товара.

Региональные фильтры должны выполняться поисковым движком, а не постфильтрацией результатов PHP.

## 11. Кабинет продавца

При создании магазина:

- регион обязателен;
- населённый пункт обязателен;
- список населённых пунктов зависит от региона;
- можно выбрать только активные записи.

При редактировании:

- изменение города журналируется;
- после изменения очищаются региональные кеши;
- поисковый индекс товаров обновляется;
- старые региональные URL товаров корректно перенаправляются или получают canonical.

## 12. Filament

Создать:

- `RegionResource`;
- `SettlementResource`;
- relation manager населённых пунктов;
- фильтры регионов и городов для продавцов и товаров.

В `SellerResource` добавить зависимые поля:

1. регион;
2. населённый пункт.

Защита:

- удаление региона с населёнными пунктами запрещено;
- удаление населённого пункта с продавцами запрещено;
- отключение населённого пункта требует подтверждения;
- dangerous bulk delete отключён;
- изменения логируются.

Отдельный фильтр должен показывать продавцов без назначенного города.

## 13. Региональные URL и маршруты

Не дублировать каждую группу маршрутов вручную.

Рекомендуется:

- ограниченный route parameter `{location}`;
- middleware определения контекста;
- helper построения URL;
- binding только активного населённого пункта;
- список зарезервированных slug.

Зарезервировать:

- `admin`;
- `account`;
- `login`;
- `register`;
- `api`;
- `storage`;
- `catalog`;
- `search`;
- `sale`;
- `shops`;
- `product`.

Неверный региональный slug возвращает 404, а не переключает пользователя на случайный город.

## 14. SEO-архитектура

### 14.1. Индексируемые страницы

Индексировать:

- региональную главную;
- региональный каталог;
- региональные категории с товарами;
- региональные страницы магазинов;
- региональные карточки товаров, если товар действительно доступен в регионе.

Не индексировать:

- пустые региональные категории;
- внутренние AJAX URL;
- страницы с техническими параметрами;
- комбинации фильтров;
- пустые результаты поиска;
- пользовательские поисковые запросы.

### 14.2. Canonical

Текущий глобальный `canonical` через `url()->current()` недостаточен.

Создать `SeoService`, который определяет canonical для каждого типа страницы.

Правила:

- региональная категория указывает canonical на собственный региональный URL;
- пагинация сохраняет canonical страницы или использует выбранную стратегию;
- UTM и технические параметры исключаются;
- фильтры цены, продавца и сортировки canonical-ятся на основную страницу;
- старые URL canonical-ятся на режим «Все регионы» либо перенаправляются после принятия стратегии;
- нельзя canonical-ить все регионы на одну страницу, иначе региональные страницы не будут индексироваться отдельно.

### 14.3. Title и description

Шаблоны:

```text
Купить товары в Тирасполе — цены магазинов | Название сайта
Телефоны в Бендерах — купить у местных продавцов | Название сайта
Магазины Рыбницы — каталог продавцов | Название сайта
```

Метаданные формируются из:

- типа страницы;
- категории;
- населённого пункта;
- ручных SEO-полей;
- безопасного шаблона по умолчанию.

Ручное значение имеет приоритет над шаблоном.

### 14.4. H1 и контент

На региональных страницах:

- один уникальный H1;
- название населённого пункта;
- корректные хлебные крошки;
- небольшой уникальный SEO-текст только при наличии полезного содержания;
- отсутствие автоматически размноженного бессмысленного текста.

### 14.5. Sitemap

Создать раздельные sitemap:

```text
/sitemap.xml
/sitemaps/locations.xml
/sitemaps/categories-{location}.xml
/sitemaps/products-{location}.xml
/sitemaps/shops-{location}.xml
```

В sitemap включать только:

- активные населённые пункты;
- активные категории с доступными товарами;
- видимые товары;
- активные магазины;
- canonical URL.

Для больших объёмов генерация выполняется очередью или командой по расписанию.

### 14.6. Robots

Закрыть от индексации:

- `/admin`;
- `/account`;
- AJAX-маршруты;
- внутренние фильтры и сортировки;
- страницы поиска;
- служебные параметры.

Не использовать `robots.txt` вместо `noindex` для страниц, которые поисковик должен сначала прочитать.

### 14.7. Structured Data

Добавить JSON-LD:

- `BreadcrumbList`;
- `Product`;
- `Offer`;
- `Organization` или `LocalBusiness` для продавца;
- региональную доступность товара при наличии корректных данных.

Данные JSON-LD должны совпадать с видимым содержанием страницы.

### 14.8. Дубли и редиректы

Матрица:

| Сценарий | Поведение |
|---|---|
| Старый URL без региона | Работает в режиме «Все регионы» |
| URL товара в неверном регионе | 404 или 301 на фактический регион по принятой стратегии |
| Отключённый населённый пункт | 301 на «Все регионы» или родительский регион |
| Изменён slug | 301 со старого slug |
| Пустая категория региона | `noindex, follow` или 404 по принятой стратегии |
| Фильтры и сортировка | canonical на базовую региональную страницу |

Redirect-стратегию необходимо утвердить до индексации.

## 15. Аналитика

События:

- открытие переключателя;
- выбор населённого пункта;
- переход между регионами;
- поиск в регионе;
- поиск без результатов;
- просмотр товара другого региона;
- изменение города продавцом.

Не хранить точный IP как бизнес-данные без необходимости.

Аналитика должна позволять ответить:

- какие города выбирают;
- сколько товаров доступно в каждом городе;
- где много пустых поисков;
- как регион влияет на просмотры и конверсию.

## 17. Безопасность и валидация

- принимать только существующий активный slug;
- не доверять ID региона из формы без проверки связи;
- населённый пункт должен принадлежать выбранному региону;
- массовое назначение местоположения доступно только администратору;
- изменение местоположения продавца проходит policy;
- slug создаётся сервером;
- SEO-поля очищаются и экранируются Blade.

## 20. Стратегия запуска

Рекомендуется feature flag:

```env
REGIONALITY_ENABLED=false
REGIONAL_URLS_ENABLED=false
REGIONAL_SEO_ENABLED=false
```

Порядок включения:

1. справочники и Filament;
2. назначение городов продавцам;
3. переключатель без фильтрации;
4. региональная фильтрация;
5. региональные URL;
6. SEO и sitemap;
7. индексация.

Каждый флаг включается отдельно после тестов и backup.

## 21. Критерии завершения

- все активные продавцы имеют населённый пункт;
- режим «Все регионы» работает;
- выбранный город сохраняется;
- каталог, поиск, магазины и AJAX изолированы по городу;
- кеши не смешивают регионы;
- старые URL работают или имеют один корректный 301;
- canonical соответствует стратегии;
- sitemap содержит только рабочие canonical URL;
- пустые и технические страницы не индексируются;
- Filament безопасно управляет справочниками;
- полный PHPUnit проходит;
- production smoke не выявляет 500, redirect-loop и SQL-ошибки.

## 22. Оценка масштаба

Ориентировочно:

- данные и Filament: 1–2 дня;
- региональный контекст и переключатель: 1 день;
- фильтрация витрины и кеши: 2–3 дня;
- поиск и региональные URL: 2–3 дня;
- SEO, sitemap и structured data: 2–3 дня;
- тестирование и запуск: 2–3 дня.

Полная качественная реализация: примерно 10–15 рабочих дней.

MVP без региональных URL и расширенного SEO: 3–5 рабочих дней.

## 23. Что нельзя делать

- хранить город свободным текстом в `sellers`;
- добавлять `region_id` каждому товару без необходимости;
- автоматически назначать всем продавцам один город;
- фильтровать результаты после пагинации;
- использовать один cache key для всех городов;
- скрытно выбирать город по IP;
- сразу удалять старые URL;
- индексировать все комбинации фильтров;
- создавать тысячи одинаковых SEO-текстов;
- включать региональные страницы в sitemap до проверки canonical и доступности товаров;
- запускать тесты на рабочей MySQL-базе.
