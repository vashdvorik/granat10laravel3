# План SEO-модернизации BIMM

## Ограничения проекта

Работа выполняется только для основной установленной темы.

Не изменять:

- `resources/views/themes/new/**`;
- NEW-шаблоны и их стили;
- бизнес-логику кабинета продавца;
- правила модерации товаров, если изменение не требуется для SEO-контроля данных.

Основные области работы:

- `resources/views/main_layots.blade.php`;
- `resources/views/product.blade.php`;
- `resources/views/catalog/**`;
- `resources/views/seller.blade.php`;
- `resources/views/search.blade.php`;
- `resources/views/salepage.blade.php`;
- SEO-сервисы, Sitemap и `robots.txt`.

## Архитектурные правила безопасности

SEO-модернизация не должна менять существующее поведение каталога, региональности, модерации, пакетов и кабинета продавца.

- Не заменять `Product::visible()` собственной SEO-выборкой. Sitemap, товарные страницы и категории должны использовать тот же механизм видимости, что и публичный каталог.
- Не обходить ограничения активного пакета, `is_active` и статуса модерации.
- Не удалять региональный контекст из сессии. Сначала разделить пользовательский выбор города и SEO-контекст, затем покрыть оба сценария тестами.
- Не менять текущие URL товаров и магазинов без инвентаризации ссылок и подготовленных 301-редиректов.
- Не изменять существующие alias товаров: это может создать 404 и потерю накопленных сигналов.
- Не запускать AI-генерацию синхронно внутри сохранения товара или категории.
- Не делать AI обязательным для публикации: при недоступности API должен работать детерминированный шаблонный генератор.
- Не изменять `resources/views/themes/new/**`, `ResolveDesign` и переключатель дизайна.
- Перед изменением Sitemap, canonical и robots добавить регрессионные тесты для глобальных и региональных URL.

## Что уже реализовано и должно быть сохранено

- `ResolveDesign` выбирает публичную тему через `DesignManager`; основная тема использует legacy-шаблоны.
- `ResolveRegionalContext` поддерживает URL города и выбор региона через сессию/куки.
- `RegionalUrlService` формирует ссылки с городом, если региональный URL включён.
- `SeoService` уже формирует title, description, robots и canonical через composer для `main_layots`.
- `SeoService` и composer `main_layots` являются общими зависимостями для legacy и NEW, поэтому изменение их результата косвенно меняет NEW.
- `Product::visible()` централизует правила публикации товара.
- `SitemapController` уже исключает недоступные товары и строит региональные URL.
- В `resources/views/product.blade.php` уже есть Product Schema и BreadcrumbList; задача — проверить и расширить их без дублирования.
- Пагинация каталога уже имеет self-canonical для страниц после первой.

Каждый этап должен начинаться с проверки текущего поведения и завершаться тестом, подтверждающим, что эти механизмы не сломались.

## Дополнительные ограничения, выявленные при сверке

- Отсутствие изображения сейчас не входит в `publicVisible` у `ProductVisibilityResolver`. Поэтому отсутствие фото не должно автоматически скрывать товар, удалять его из публичного URL или блокировать публикацию.
- Пустая страница магазина или категории сейчас может отвечать `200`. До отдельного решения не менять её на `404`; для SEO безопаснее сначала использовать `noindex, follow`, сохранив пользовательский маршрут.
- Sitemap работает в двух режимах: при выключенных региональных URL глобальная карта и при включённых региональных URL формируются по разным правилам. Нельзя менять формат Sitemap без тестов обоих режимов.
- `REGIONAL_SEO_ENABLED` сейчас управляет выводом canonical, robots и description в основном layout. Не включать и не выключать этот флаг глобально во время внедрения без проверки всех публичных страниц.
- Основной legacy-шаблон уже содержит Open Graph и Product Schema. Новая реализация должна исправлять или дополнять текущую разметку, а не добавлять параллельный SEO-шаблон.
- Общие SEO-классы нельзя менять только для legacy без изоляции: использовать legacy-адаптер или явную проверку темы, сохраняя прежний результат для NEW.
- Пользовательская региональность через cookie должна сохраняться. Для SEO сначала нужно доказать, что прямой запрос без cookie получает стабильный контент.
- SEO-проверка наличия фото должна быть рекомендацией, а не новой причиной скрытия товара: текущая бизнес-логика допускает отображение товара с заглушкой.

## Цели

1. Сделать публичную часть понятной для Google и других поисковых систем.
2. Обеспечить корректную индексацию товаров, категорий, магазинов и региональных страниц.
3. Автоматически формировать SEO-данные товаров и категорий без участия продавца.
4. Исключить дубли, технические страницы, пустые посадочные страницы и битые URL.
5. Подготовить проект к измеримому росту органического трафика.

Первая страница поиска не может быть гарантирована только изменениями кода: на результат влияют конкуренция, спрос, качество данных, поведение пользователей и внешние ссылки. План создаёт техническую и контентную основу для роста позиций.

## Этап 0. SEO-инвентаризация и базовые показатели

### Задачи

- Составить список всех публичных типов страниц и URL.
- Разделить страницы на индексируемые и технические.
- Зафиксировать текущие значения `title`, `description`, H1 и canonical.
- Проверить существующие товары, категории, магазины и региональные страницы.
- Подготовить выгрузку страниц с ошибками 404, дублями и отсутствующими данными.
- Подключить Google Search Console и Яндекс Вебмастер, если они ещё не подключены.

### Результат

Таблица SEO-состояния страниц и исходные показатели:

- количество индексируемых URL;
- количество товаров в Sitemap;
- количество ошибок индексации;
- показы и клики;
- средняя позиция по группам запросов;
- количество страниц с дублирующими мета-данными.

## Этап 1. Кодировка и единый SEO-слой основной темы

### Задачи

- Исправить повреждённые русские строки в SEO-сервисах и основной теме.
- Проверить кодировку базы данных, PHP-файлов, Blade-шаблонов и HTTP-заголовков.
- Сохранить текущий composer `main_layots` как точку подключения SEO-данных.
- Убрать только дублирование формирования SEO-текстов из отдельных legacy-шаблонов.
- Оставить единый источник для `title`, `description`, canonical и robots.
- Добавить тесты на корректную кириллицу в исходном HTML.

Не переносить SEO composer или SEO-разметку в NEW-тему.

Если изменение требуется в общем `SeoService`, сначала добавить тесты на сохранение текущего результата NEW и только затем включать новый результат для legacy.

### Результат

Любая публичная страница основной темы отдаёт корректный UTF-8 HTML с предсказуемыми SEO-данными.

## Этап 2. Проверка регионального контекста, URL и canonical

### Задачи

- Утвердить основной формат URL для глобальных и региональных страниц.
- Определить, какая версия товара является canonical при наличии регионального URL.
- Сначала составить карту текущих глобальных и региональных URL.
- Настроить 301-редиректы только после подтверждения старого и нового канонического адреса.
- Сохранить выбор города через сессию и cookie для обычных пользователей.
- Для поисковых роботов и прямых SEO-URL обеспечить детерминированный контекст без пользовательской cookie.
- Не менять поведение глобального каталога до отдельного теста с cookie города.
- Передавать фильтры только через URL-параметры.
- Для страниц с фильтрами использовать уже существующее правило `noindex, follow` и canonical на базовую страницу, не меняя бизнес-логику фильтров.
- Проверить работу canonical на пагинации.

### Критерии готовности

- Один индексируемый URL соответствует одной версии контента.
- Один товар не конкурирует сам с собой через несколько canonical URL.
- Фильтр каталога не меняет содержимое страницы без изменения URL.

## Этап 3. Robots и индексация

### Задачи

- Обновить `public/robots.txt`.
- Добавить ссылку на Sitemap.
- Закрыть от индексации:
  - аккаунт продавца;
  - заказы;
  - избранное;
  - внутренний поиск;
  - AJAX-маршруты;
  - страницы с техническими параметрами;
  - пустые и временные страницы.
- Оставить доступными для индексации товары, категории, магазины и полезные региональные страницы.
- Пустые магазины и категории не удалять автоматически: сохранять текущий ответ маршрута и добавлять `noindex, follow` только после отдельного теста.
- Проверить, что robots не блокирует CSS, JavaScript и изображения, необходимые для отображения страницы.

## Этап 4. Безопасное расширение Sitemap

### Задачи

- Сначала сохранить доступный маршрут `/sitemap.xml` и его XML-формат.
- Покрыть текущий Sitemap регрессионными тестами.
- Только после этого при необходимости создать Sitemap Index.
- Разделить карты сайта:
  - товары;
  - категории;
  - магазины;
  - региональные страницы.
- Добавить `lastmod` на основании `updated_at`.
- Исключать скрытые, неактивные, удалённые и недоступные товары через `Product::visible()`.
- Не добавлять пустые категории и города.
- Формировать Sitemap пакетно, чтобы проект не загружал все URL в память одним запросом.
- Зарегистрировать Sitemap в Google Search Console и Яндекс Вебмастере.

## Этап 5. Мета-данные основной темы

Для каждого типа страницы определить автоматические шаблоны.

### Товар

Пример Title:

`Наушники Apple AirPods 4 — цена в Тирасполе | BIMM`

Формировать:

- Title;
- Meta Description;
- один H1;
- Open Graph;
- Twitter Card;
- canonical;
- robots.

### Категория

Пример Title:

`Наушники в Тирасполе — купить у местных продавцов | BIMM`

Использовать:

- название категории;
- город;
- количество доступных предложений;
- дочерние категории.

### Магазин

Пример Title:

`Магазин электроники «Название» в Тирасполе | BIMM`

Не использовать одинаковое шаблонное описание для всех магазинов.

## Этап 6. Аудит и расширение товарной микроразметки

На основной странице товара проверить уже существующий JSON-LD в `resources/views/product.blade.php` и аккуратно расширить его при необходимости:

- `Product`;
- `Offer`;
- `BreadcrumbList`;
- продавца;
- категорию;
- актуальную цену;
- валюту;
- наличие;
- главное изображение;
- описание.

Правила:

- разметка должна присутствовать в исходном HTML;
- цена в разметке должна совпадать с видимой ценой;
- наличие должно соответствовать фактическому состоянию товара;
- не добавлять выдуманные отзывы, рейтинг и бренд;
- если бренд неизвестен, не формировать его из названия продавца.

Не добавлять второй комплект Schema в тот же legacy-шаблон и не переносить эту разметку в NEW.

Также проверить валидность разметки через Rich Results Test и отчёт Merchant listings в Google Search Console.

## Этап 7. Безопасная автоматизация SEO товаров

Продавец не должен заполнять SEO-поля вручную.

При создании или изменении товара система автоматически формирует SEO-представление, не меняя существующую бизнес-логику публикации:

1. Нормализует название.
2. Удаляет мусорные символы и повторения.
3. Проверяет категорию, город и продавца.
4. Формирует SEO Title.
5. Формирует Meta Description.
6. Создаёт `alt` главного изображения.
7. Проверяет длину и уникальность мета-данных.
8. Обновляет SEO при изменении названия, категории, города или цены.

### Уровни генерации

#### Базовый уровень — всегда доступен

Детерминированные шаблоны на основе реальных данных товара:

`Купить {название} в {городе}. Цена, фото и контакты продавца на BIMM.`

#### Расширенный уровень — после сохранения, через очередь

AI может улучшать описание и характеристики, но только после проверки:

- запрет выдуманных свойств;
- запрет неподтверждённых гарантий;
- запрет рекламного переспама;
- ограничение длины;
- проверка языка и кодировки;
- резервный переход на шаблон при ошибке API.

AI-задача не должна блокировать сохранение, модерацию или публикацию товара. SEO не должно зависеть от доступности AI API.

На первом этапе предпочтительно не добавлять новые обязательные SEO-поля в таблицу `products`. Сначала использовать отдельный `SeoService` с детерминированными шаблонами. Персистентные SEO-поля добавлять только после отдельного решения о миграции и обратной совместимости.

## Этап 8. Безопасная автоматизация SEO категорий

Для каждой активной категории автоматически формировать:

- Title;
- Meta Description;
- H1;
- короткое вступительное описание;
- BreadcrumbList;
- дочерние категории;
- популярные товары;
- ссылки на магазины с предложениями.

### Условия индексации категории

Категория индексируется только если:

- активна;
- содержит опубликованные товары;
- имеет понятное название;
- не является пустым дублем другой категории.

AI-описания категорий разрешать только при наличии реального ассортимента и обязательной проверке уникальности. Не изменять `Category::desc` автоматически без отдельного подтверждения администратора; на первом этапе использовать SEO-представление через сервис.

## Этап 9. Региональное SEO

Для страниц формата `{город} + {категория}` использовать отдельные URL только при наличии достаточного ассортимента.

Такая страница должна иметь:

- уникальный город в Title и H1;
- товары только этого города;
- уникальное описание ассортимента;
- корректный canonical;
- собственные ссылки в Sitemap;
- внутренние ссылки из каталога и региональных страниц.

Пустые города и категории не индексировать.

## Этап 10. Внутренняя перелинковка без изменения маршрутов

Добавить автоматические связи:

- главная → популярные категории;
- категория → подкатегории;
- категория → товары;
- товар → категория;
- товар → магазин;
- товар → похожие товары;
- магазин → категории товаров;
- город → категории города.

Цель — исключить страницы-сироты и сократить глубину вложенности важных товаров. Все ссылки должны создаваться через `RegionalUrlService`, чтобы не потерять текущий региональный контекст.

## Этап 11. Изображения и скорость

- Конвертировать изображения в WebP/AVIF.
- Добавлять `width` и `height`.
- Использовать lazy-loading для изображений ниже первого экрана.
- Загружать главное изображение товара с приоритетом.
- Формировать SEO-friendly `alt` автоматически.
- Устранить скачки layout из-за изображений без размеров.
- Проверить мобильные Core Web Vitals.
- Не ухудшать работу основной установленной темы.

## Этап 12. SEO-контроль без изменения модерации

Перед публикацией автоматически проверять:

- название;
- категорию;
- цену;
- изображение;
- описание;
- отсутствие мусорных символов;
- отсутствие повторяющегося названия;
- наличие Title и Description;
- допустимую длину мета-данных;
- корректность изображения и `alt`.

Блокирующими должны быть только ошибки, действительно мешающие индексации или пониманию товара. Остальные замечания показывать как рекомендации. SEO-проверка не должна подменять AI/ручную модерацию и не должна самостоятельно менять статус товара.

## Этап 13. Мониторинг

Создать административный отчёт:

- товары без описания;
- товары без изображений;
- дубли Title;
- дубли Description;
- пустые категории;
- ошибки Sitemap;
- ошибки JSON-LD;
- 404-страницы;
- страницы, исключённые из индексации;
- товары без кликов и показов.

Проверять проект после каждого SEO-релиза:

- Google Search Console;
- Яндекс Вебмастер;
- Rich Results Test;
- Lighthouse;
- Sitemap Validator;
- проверка HTTP-кодов;
- проверка canonical;
- проверка UTF-8.

## Критерии завершения

- Все индексируемые страницы имеют один понятный canonical.
- В Sitemap находятся только доступные публичные страницы.
- Поиск, кабинет, заказы и технические маршруты не индексируются.
- Нет повреждённой кодировки в Title, Description, H1 и JSON-LD.
- Товарная разметка проходит проверку.
- SEO-данные товара формируются автоматически без участия продавца.
- SEO-данные категорий формируются автоматически и не создают дубли.
- Изменение товара обновляет мета-данные, Sitemap и поисковый индекс.

## Обязательная последовательность внедрения

1. Сначала добавить тесты текущих глобальных, региональных, фильтрованных и пагинированных страниц.
2. Затем исправить кодировку SEO-строк без изменения маршрутов.
3. Затем проверить и дополнить существующий SEO composer.
4. Затем проверить Product Schema в legacy-шаблоне без добавления дубликатов.
5. Затем изменить robots и Sitemap с регрессионной проверкой XML.
6. Затем внедрить детерминированную автоматическую генерацию SEO-представления товара и категории.
7. AI-генерацию подключать последней и только асинхронно.

Если тесты обнаруживают изменение видимости товара, региональной выборки, URL, статуса модерации или поведения кабинета, этап останавливается до выяснения причины.
