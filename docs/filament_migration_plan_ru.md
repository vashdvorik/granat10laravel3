# План миграции админки с Voyager на Filament

## Цель

Перенести административную часть проекта из Voyager на Filament так, чтобы:
- не сломать существующую логику;
- сохранить управление моделями, страницами и логами;
- выполнить миграцию поэтапно;
- оставить возможность отката на Voyager до полной проверки.

## Текущее состояние проекта

- Проект на Laravel 10.
- Voyager подключён в `routes/web.php` как `Voyager::routes()` внутри `admin`-группы.
- В `composer.json` используется `tcg/voyager: 1.7`.
- В проекте есть кастомные админ-страницы:
  - `admin.activity-log` (`App\Http\Controllers\Admin\ActivityLogController`);
  - `admin.category-tree` (`App\Http\Controllers\Admin\CategoryTreeController`).
- Эти страницы строятся на базе шаблона `voyager::master` и используют Voyager UI.
- За доступ к админке отвечает middleware `App\Http\Middleware\EnsureAdminAccess` и Gate `access-admin`.
- В проекте есть Backend-кабинет продавца и публичная витрина, которые миграции не касаются напрямую.
- В проекте используется `spatie/laravel-activitylog`, `kalnoy/nestedset`.

## Основные точки риска

- Удаление Voyager до замены всех страниц приведёт к падению `/admin`.
- Пользовательские шаблоны и страницы на Voyager должны быть перенесены отдельно.
- Доступ основан на Voyager permission `browse_admin`; hardcoded email удалён.
- Возможно, в базе уже настроены Voyager BREAD, меню и permissions.
- Категории строятся как дерево, а лог действий имеет собственную фильтрацию.

## Общая стратегия

1. **Аудит текущих зависимостей и данных.**
2. **Установка Filament без удаления Voyager.**
3. **Пошаговая сборка Filament-ресурсов и страниц.**
4. **Проверка доступа и ролей.**
5. **Параллельный запуск Voyager + Filament в режиме «пилот».**
6. **Перенос пользовательских admin-views.**
7. **Проверка тестами и ручная регрессия.**
8. **Отключение Voyager только после завершения всех проверок.**

## Детальный план миграции

### Шаг 1. Подготовка и аудит

- Создать ветку `migration/voyager-to-filament`.
- Выполнить полный список Voyager-роутов и BREAD в админке.
- Найти все пользовательские admin-views:
  - `resources/views/admin/activity-log`;
  - `resources/views/admin/category-tree`;
  - другие файлы, которые используют `voyager::master`.
- Зафиксировать все изменения в `config/voyager.php`.
- Проверить, какие модели и таблицы управляются через Voyager.
- Проверить, какие роли/permissions существуют в базе Voyager (`roles`, `permissions`, `permission_role`, `data_types`, `data_rows`).

### Шаг 2. Установка Filament

- Добавить пакет Filament в проект: `composer require filament/filament`.
- Если потребуется, установить `filament/forms`, `filament/tables` и другие зависимости.
- Опубликовать конфигурацию Filament: `php artisan vendor:publish --tag=filament-config`.
- При необходимости установить Filament Bootstrap/AlpineJS зависимости.
- Настроить `filament.php` в соответствии с имеющейся auth-системой:
  - guard `web`;
  - login route если используется Fortify;
  - middleware `auth`.

### Шаг 3. Сохранение текущего доступа и авторизации

- Повторно использовать Gate `access-admin` для Filament.
- Настроить Filament так, чтобы панель была доступна только авторизованным пользователям с permission `browse_admin`.
- Не добавлять отдельную проверку email и не дублировать правила Voyager.

### Шаг 4. Миграция моделей и ресурсов

- Проанализировать модели, которые управляются через Voyager:
  - `User`;
  - `Seller`;
  - `Product`;
  - `Package`;
  - `Category`;
  - `SellerPackage`;
  - возможно, `Image` и другие.
- Для каждой модели создать Filament Resource:
  - `UserResource`, `SellerResource`, `ProductResource`, `PackageResource`, `CategoryResource`, `SellerPackageResource`.
- Для каждой Resource определить:
  - формы и поля, соответствующие текущим BREAD-правилам;
  - таблицу и фильтры;
  - relation manager`ы, если нужно;
  - guards/permissions.
- Отдельно перенести все поля Tree-структуры для `Category`.
- Если какие-то BREAD-поля требовали кастомной логики, реализовать их в Filament с помощью custom components.

### Шаг 5. Перенос пользовательских страниц

- Перенести страницу `admin.activity-log` на Filament Page:
  - `ActivityLogPage` в каталоге `App\Filament\Pages`.
  - Сохранить фильтрацию `log_name`, `search`, `causer`.
  - Сформировать таблицу с модальными деталями или детализированную страницу.
- Перенести страницу `admin.category-tree` на Filament Page:
  - `CategoryTreePage`.
  - Сохранить дерево категорий из `Category::defaultOrder()->get()->toTree()`.
  - Сделать expand/collapse на Filament UI.
- Отдельно сделать страницу `Dashboard` для Filament, если нужно.

### Шаг 6. Миграция меню и навигации

- Настроить Filament Navigation в `App\Filament\Navigation` или `filament.php`.
- Добавить разделы:
  - Управление пользователями;
  - Товары;
  - Магазины / Продавцы;
  - Пакеты;
  - Категории;
  - Журнал действий.
- Скрывать пункты навигации по правам доступа.
- Оставить Voyager-меню без изменений до полной проверки.

### Шаг 7. Параллельный режим и проверка

- Развернуть Filament на `/admin/filament` или `/filament` на этапе тестирования.
- Оставить текущий Voyager-путь `/admin` до тех пор, пока Filament полностью не заменит админку.
- Проверить:
  - вход в Filament по тем же учетным данным;
  - корректность CRUD-операций;
  - маршруты и доступы;
  - поведение пользовательских страниц.

### Шаг 8. Перенос ролей и прав

- Если роли и permissions управляются через Voyager, создать миграцию для переноса в Laravel/Filament:
  - `roles`;
  - `permissions`;
  - `permission_role`;
  - связи `User`-`Role`.
- Настроить Filament Authorization:
  - `canAccessFilament` на модели `User`;
  - `Filament::serving` event, если используются динамические правила;
  - `Permissions` через `spatie/laravel-permission` или встроенные политики.
- Убедиться, что роль `admin` сохраняет доступ к новой панели.

### Шаг 9. Проверка бизнес-логики

- Пропускать через тесты следующие сценарии:
  - добавление / редактирование / удаление товара;
  - управление категориями;
  - управление пакетами и лимитами;
  - изменение баланса / статуса продавца;
  - действия в журнале активности.
- Проверить, что логика кабинета продавца и public-части не ломается.
- Убедиться, что импорт/экспорт данных из Voyager не требуется, если структура данных остается прежней.

### Шаг 10. Удаление Voyager

- После полной проверки отключить `Voyager::routes()`.
- Удалить Voyager-маршруты, но сохранить Gate `access-admin` для Filament.
- Убрать `tcg/voyager` из `composer.json`.
- Удалить `config/voyager.php` и все кастомные Voyager views после проверки.
- Удалить записи Voyager BREAD из базы, если они больше не нужны.

## Рекомендации по разделению работ

- Первое изменение: установить Filament и настроить базовый вход.
- Второе изменение: создать Filament Resource для одной модели, например `Product`.
- Третье изменение: перенести пользовательскую страницу `activity-log`.
- Четвёртое изменение: создать `CategoryTreePage`.
- Пятое изменение: отключить Voyager только после завершения полного списка проверок.

## Что не менять в процессе

- Не менять архитектуру public-витрины и кабинета продавца.
- Не трогать `routes/account` и публичные `catalog`-роуты.
- Не удалять Voyager сразу.
- Не переносить все сразу в один коммит: админку нужно мигрировать по частям.
- Не менять логику тарифов и баланса без тестов.

## Проверка успеха

Проект считается успешно мигрированным, если:
- Filament-панель работает;
- CRUD-механика для ключевых моделей работает;
- кастомные страницы `activity-log` и `category-tree` отображаются;
- пользователей с ролью `admin` пускают в Filament;
- `Voyager::routes()` можно отключить без падения других страниц;
- `php artisan test` проходит по основным сценариям.

## Примечание

Этот документ служит инструкцией для поэтапного переноса админки. Первоначально нужно сохранить работу старой админки, затем мигрировать каждое админское представление и только после этого удалять Voyager.
