# План оптимизации AI-модерации товаров

## 1. Назначение документа

Документ описывает план исправления и оптимизации модерации текстов и изображений товаров через AI API, а также управления модерацией в Filament.

Основные цели:

- полностью разделить модерацию текста и изображений;
- безопасно переключать провайдеров через Filament;
- не изменять уже поставленные в очередь задания при переключении модели;
- сохранить полную и неизменяемую историю проверок;
- уменьшить количество и стоимость API-запросов;
- исключить автоматическую публикацию товара после неполной проверки;
- обеспечить безопасный переход на ручную модерацию при сбоях.

## 2. Целевая архитектура

Модерация должна состоять из независимых этапов:

```text
Товар
  ├─ Локальные проверки
  ├─ Проверка текста → DeepSeek или Gemini
  ├─ Safety-проверка изображений → OpenAI omni-moderation-latest
  ├─ Проверка правил маркетплейса → Gemini Vision
  ├─ OCR и поиск контактов → локальные правила
  └─ Агрегатор решений → публикация, исправление или ручная проверка
```

Для каждого контура отдельно задаются:

- состояние: включён или выключен;
- режим: `shadow`, `manual` или `auto`;
- провайдер и модель;
- API-ключ и базовый URL;
- очередь, таймаут и количество попыток;
- часовые и дневные лимиты;
- версия конфигурации и политики.

## 3. Критические исправления — P0

### 3.1. Разделение конфигураций провайдеров

Нельзя использовать один API-ключ, модель и URL для разных провайдеров. Необходимо создать независимые настройки:

- текст: DeepSeek;
- текст: Gemini;
- изображения: OpenAI Moderation;
- изображения: Gemini Vision.

Рекомендуется хранить секреты в зашифрованной таблице настроек. Существующие переменные `.env` временно оставить как fallback для обратной совместимости.

### 3.2. Версионирование конфигурации

При каждом сохранении настроек должна создаваться версия конфигурации. В задание очереди необходимо передавать:

- канал `text` или `image`;
- провайдера;
- модель;
- версию конфигурации;
- версию политики;
- версию содержимого товара.

Секретный API-ключ нельзя сериализовать в задание. Задание должно получать его из зашифрованной конфигурации по идентификатору версии.

Переключение провайдера в Filament не должно менять поведение уже поставленных в очередь заданий.

### 3.3. Неизменяемая история запусков

Завершённые и неудачные записи модерации нельзя переводить в состояние `retrying` или очищать.

Каждый повторный запуск должен создавать новую запись со следующими полями:

- `retry_of_id`;
- `attempt_number`;
- `configuration_version`;
- `provider`;
- `model`;
- время начала и завершения;
- результат или ошибка.

### 3.4. Исправление shadow-режима

В режиме `shadow` должны выполняться все этапы проверки текста и изображений. Результаты сохраняются, но не изменяют:

- статус товара;
- `is_active`;
- публикацию;
- решение действующего модератора.

### 3.5. Безопасное включение автоматического режима

Filament не должен разрешать включение `auto`, если:

- API-ключ выбранного провайдера отсутствует;
- тест подключения не пройден;
- модель не поддерживает требуемый тип данных;
- worker очереди недоступен;
- конфигурация невалидна.

## 4. Оптимизация управления в Filament

Настройки следует разделить на две независимые вкладки.

### 4.1. Модерация текста

Показывать:

- включение контура;
- режим работы;
- активного провайдера;
- модель и URL;
- состояние ключа выбранного провайдера;
- кнопку проверки подключения;
- очередь и состояние worker;
- лимиты и текущий расход;
- последнюю успешную проверку;
- последнюю ошибку.

### 4.2. Модерация изображений

Показывать те же данные независимо от текстового контура. Ключ изображения не должен влиять на индикатор готовности текстовой модерации и наоборот.

### 4.3. Управление изменениями

Добавить:

- предварительную проверку конфигурации;
- предупреждение о заданиях в очереди;
- подтверждение переключения провайдера;
- журнал действий администратора;
- возможность отката на предыдущую версию;
- отдельную временную остановку текста и изображений.

## 5. Оптимизация текстовой модерации

Перед обращением к AI выполнять локальные проверки:

- телефоны и мессенджеры;
- ссылки и домены;
- запрещённые слова;
- слишком короткий или пустой текст;
- подозрительные цены;
- дублирующиеся объявления;
- обход правил маркетплейса.

В AI-запрос отправлять только необходимые поля. Ответ должен быть коротким и строго структурированным JSON.

Для сокращения расходов:

- ограничить максимальный размер текста;
- вычислять fingerprint модерируемого содержимого;
- повторно использовать результат неизменившегося текста;
- не отправлять запрос после безусловного запрета локальными правилами;
- повторно проверять только изменившиеся поля.

## 6. Оптимизация изображений

### 6.1. Локальная подготовка

До вызова AI проверять:

- наличие файла;
- MIME-тип;
- размер и разрешение;
- повреждение файла;
- дубликаты изображений.

Для AI создавать оптимизированную копию подходящего разрешения, не изменяя оригинал.

### 6.2. Разделение ответственности моделей

`omni-moderation-latest` использовать как safety-фильтр для опасного и запрещённого визуального содержания.

Не считать его достаточным для проверки:

- соответствия фотографии товару;
- контактов, ссылок и QR-кодов;
- документов и денег;
- пустых или нерелевантных изображений;
- соответствия категории маркетплейса.

Для этих задач использовать Gemini Vision, OCR и локальные правила. Если обязательная проверка не выполнена, товар нельзя автоматически одобрять.

### 6.3. Независимая проверка изображений

Каждое изображение должно иметь собственный результат:

- ID и индекс изображения;
- hash файла;
- провайдера и модель;
- решение и риск;
- категории нарушений;
- сообщение продавцу;
- provider request ID.

При замене одной фотографии повторно проверяется только она.

В safety-запрос OpenAI нельзя добавлять название, описание или категорию товара как пользовательский текст: текстовая информация должна проверяться отдельным контуром.

## 7. Агрегация решений

Итоговое решение формирует отдельный сервис, а не конкретный API-клиент.

| Ситуация | Итоговое действие |
|---|---|
| Все обязательные проверки успешно пройдены | Автоматическое одобрение |
| Провайдер временно недоступен | Retry, затем ручная проверка |
| Результат неоднозначный | Ручная проверка |
| Найдено исправимое нарушение | Вернуть продавцу на исправление |
| Найдено критическое нарушение | Отклонить товар |
| Провайдер не поддерживает обязательную проверку | Не одобрять автоматически |

Нарушения следует разделить по типу реакции:

- `seller_actionable` — продавец может исправить;
- `admin_review_only` — требуется решение модератора;
- `hard_reject` — публикация запрещена.

Общий флаг OpenAI без конкретного исправляемого нарушения должен вести в ручную проверку, а не автоматически в `ChangesRequired`.

## 8. Оптимизация очередей

Рекомендуемые очереди:

- `moderation-text`;
- `moderation-images`;
- `moderation-retry`.

Для каждой очереди отдельно настроить:

- timeout;
- число попыток;
- exponential backoff;
- лимиты провайдера;
- приоритет;
- мониторинг зависших заданий.

Перед применением результата задание повторно проверяет версию товара. После исчерпания попыток товар автоматически переводится на ручную проверку, а не остаётся в `Processing`.

## 9. Интерфейс ручной модерации

На странице товара модератор должен видеть:

- текущую версию товара;
- результат локальных правил;
- отдельный результат проверки текста;
- результат каждого изображения;
- провайдера, модель и версию политики;
- риск и найденные нарушения;
- историю всех попыток;
- изменения продавца между версиями.

Необходимые действия:

- одобрить;
- запросить исправления;
- отклонить;
- повторить только текст;
- повторить выбранное изображение;
- повторить через другого провайдера;
- отметить ошибочное решение AI.

## 10. Мониторинг стоимости и качества

Метрики рассчитываются отдельно для каждого канала и провайдера:

- количество запросов;
- среднее и максимальное время ответа;
- ошибки API;
- расход лимитов и стоимость;
- количество pending, processing, failed и stuck;
- процент автоматического одобрения;
- процент ручных проверок;
- расхождения AI и модераторов;
- ложные срабатывания.

При исчерпании бюджета система должна безопасно перейти в ручной режим и уведомить администратора.

## 11. Этапы реализации

### Этап A — критическая безопасность

1. Разделить настройки и ключи провайдеров.
2. Добавить версии конфигурации.
3. Зафиксировать конфигурацию в заданиях очереди.
4. Сделать историю запусков неизменяемой.
5. Исправить повторные запуски.
6. Исправить полный конвейер shadow-режима.
7. Добавить проверки подключения в Filament.

### Этап B — снижение расходов

1. Расширить локальные правила.
2. Добавить fingerprints и кэширование результатов.
3. Проверять только изменившиеся поля и изображения.
4. Уменьшать копии изображений перед отправкой.
5. Добавить OCR для контактов, ссылок и QR-кодов.
6. Разделить лимиты по каналам и провайдерам.

### Этап C — качество и эксплуатация

1. Переработать экран настроек Filament.
2. Улучшить карточку ручной модерации.
3. Добавить раздельные метрики.
4. Добавить аудит настроек и откат.
5. Ввести разные политики для категорий товаров.

## 12. Безопасное внедрение

1. Покрыть критические сценарии автоматическими тестами.
2. Развернуть новую архитектуру с выключенным auto-режимом.
3. Запустить полный shadow-конвейер.
4. Сравнивать результаты AI с решениями модераторов.
5. Настроить пороги на реальных данных.
6. Включить auto сначала для категорий с низким риском.
7. Постепенно подключать остальные категории.
8. Сохранить административный аварийный выключатель и откат.

## 13. Критерии готовности

Оптимизация считается завершённой, когда:

- переключение провайдера не уничтожает настройки другого провайдера;
- уже поставленное задание выполняется на зафиксированной модели;
- текст и изображения имеют независимые ключи, лимиты и статусы;
- shadow-режим выполняет весь конвейер без изменения товара;
- retry создаёт новую попытку и сохраняет историю;
- результат привязан к конкретному изображению;
- отсутствие обязательной проверки блокирует auto-одобрение;
- сбой API переводит товар на ручную проверку;
- Filament достоверно показывает состояние каждого контура;
- стоимость и качество измеряются отдельно по каждому провайдеру.

## 14. Рекомендуемая экономичная схема

```text
Локальные правила
  → DeepSeek для текста
  → OpenAI omni-moderation-latest для safety-проверки изображений
  → OCR и локальные проверки контактов
  → Gemini Vision только для сложных или сомнительных случаев
  → ручная модерация как безопасный fallback
```

Такая схема сокращает дорогие vision-запросы, сохраняет полноту проверки маркетплейса и не смешивает текстовую модерацию с анализом изображений.
