# Архив: инструкция по устранению UX-проблем модерации товаров

## 1. Цель

Сделать путь продавца предсказуемым:

1. Продавец сохраняет черновик или отправляет товар на проверку.
2. Система явно показывает текущий этап.
3. При безопасном результате товар публикуется автоматически.
4. При сомнении товар проверяет администратор.
5. Технические ошибки не перекладываются на продавца.
6. В каждый момент пользователю доступно одно понятное основное действие.

## 2. Главная архитектурная проблема

Поле `products.is_active` сейчас используется сразу в двух значениях:

- продавец хочет опубликовать товар;
- товар фактически опубликован.

Из-за этого результат одобрения зависит от предыдущего технического значения поля. Необходимо разделить намерение продавца и реальную публикацию.

## 3. Целевая модель данных

### 3.1. Добавить поле намерения публикации

Добавить в `products`:

```text
publication_requested boolean default false
```

Значения:

- `true` — после успешной модерации товар нужно опубликовать;
- `false` — после успешной модерации товар должен остаться скрытым.

### 3.2. Оставить `is_active` только для фактической публикации

После изменения:

- `is_active = true` означает, что товар реально виден покупателям;
- форма продавца не должна напрямую записывать пользовательский выбор в `is_active`;
- при отправке на модерацию `is_active` всегда остаётся `false`;
- при одобрении публикация определяется через `publication_requested`.

### 3.3. Миграция существующих данных

Для существующих записей:

```text
publication_requested = is_active
```

После этого не менять `is_active` до принятия решения модерацией.

## 4. Целевая матрица статусов

| Статус | Что видит продавец | Основное действие | Публикация |
|---|---|---|---|
| `draft` | Черновик | Отправить на проверку | Нет |
| `pending` | Ожидает проверки | Нет, только ожидание | Нет |
| `processing` | Проверяется | Нет, только ожидание | Нет |
| `needs_review` | На проверке у администратора | Нет, только ожидание | Нет |
| `changes_required` | Нужны исправления | Исправить товар | Нет |
| `rejected` | Не может быть опубликован | Исправить или удалить | Нет |
| `approved` + `is_active=false` | Одобрен, но скрыт | Опубликовать | Нет |
| `approved` + `is_active=true` | Опубликован | Поднять | Да |

Статус `failed` не должен быть пользовательским состоянием.

## 5. Обработка технических ошибок

### 5.1. Во время повторных попыток

Продавец продолжает видеть:

```text
Модерация: Проверяется
Публикация: Не опубликован
```

Технические детали сохраняются только в `product_moderation_runs`.

### 5.2. После исчерпания попыток

Товар автоматически переводится в:

```text
needs_review
```

Продавец видит:

```text
Модерация: На проверке у администратора
Публикация: Не опубликован
Товар передан администратору для дополнительной проверки.
```

Администратор видит техническую причину в журнале запусков.

### 5.3. Удаление пользовательского `failed`

Необходимо:

1. Не создавать новые товары со статусом `failed`.
2. Перевести существующие `failed` в `needs_review`.
3. Удалить кнопку повтора проверки из кабинета продавца.
4. Оставить административный повтор только как техническое действие.
5. Позже удалить `Failed` из enum после миграции данных и тестов.

## 6. Однозначное одобрение

При одобрении товара:

```text
is_active = publication_requested
moderated_version = moderation_version
moderation_status = approved
```

Результат:

- продавец просил публикацию — товар сразу публикуется;
- продавец сохранил товар без намерения публикации — товар остаётся одобренным, но скрытым.

Администратор должен заранее видеть результат кнопки:

- `Одобрить и опубликовать`;
- `Одобрить без публикации`.

Название действия определяется значением `publication_requested`.

## 7. Формы создания и редактирования

### 7.1. Создание

Заменить техническое поле `is_active` на пользовательский выбор:

```text
После сохранения:
● Отправить на проверку и опубликовать после одобрения
○ Сохранить как черновик
```

В запросе это значение должно преобразовываться в:

```text
publication_requested
```

### 7.2. Редактирование

Если изменились контролируемые модерацией данные:

1. `is_active = false`;
2. увеличить `moderation_version`;
3. сбросить прошлое одобрение;
4. сохранить выбор в `publication_requested`;
5. отправить товар на проверку, если пользователь выбрал отправку.

Если изменились только некритичные поля, интерфейс не должен обещать повторную модерацию.

### 7.3. Явно определить контролируемые поля

Проверять повторно:

- название;
- описание;
- характеристики;
- цена и скидочная цена;
- категория;
- изображения.

Не требовать повторной модерации для безопасных служебных изменений, если они появятся в дальнейшем.

## 8. Карточка товара продавца

### 8.1. Информационный блок

Показывать только:

```text
Модерация: [понятный статус]
Публикация: [опубликован / не опубликован]
[одно поясняющее предложение]
```

Не дублировать `moderation_summary` и описание статуса.

### 8.2. Основное действие

Показывать только действие, которое пользователь действительно может выполнить:

- `draft` — «Отправить на проверку»;
- `changes_required` — «Исправить»;
- `approved`, скрыт — «Опубликовать»;
- опубликован — «Поднять»;
- ожидание проверки — основная кнопка отсутствует.

Не показывать отключённую кнопку «Поднять» для черновиков и товаров на проверке.

### 8.3. Дополнительные действия

В меню `⋮` оставить:

- снять с публикации;
- удалить;
- технически допустимые второстепенные действия.

«Изменить» можно оставить постоянной кнопкой.

## 9. Интерфейс администратора

### 9.1. Действия модерации

Для `pending`, `needs_review` и временно существующего `failed`:

- одобрить;
- отправить на доработку;
- отклонить.

Для `processing` ручные решения скрыть, чтобы администратор не конфликтовал с выполняющимся заданием.

### 9.2. Технический повтор

Кнопку «Повторить ИИ-проверку» показывать только администратору и только если:

- последний запуск завершился ошибкой;
- нет активного задания текущей версии;
- ИИ-модерация включена.

Повтор не должен заменять возможность ручного решения.

### 9.3. Информация в таблице

Показывать:

- пользовательский статус;
- публикацию;
- продавца;
- дату отправки;
- индикатор технической ошибки без вывода подробностей в основную таблицу.

Подробности ошибки оставить во вкладке запусков модерации.

## 10. Уведомления продавца

Добавить уведомления для всех конечных решений.

### Автоматическое одобрение

```text
Товар «Название» прошёл проверку и опубликован.
```

Или:

```text
Товар «Название» прошёл проверку и готов к публикации.
```

### Передача администратору

```text
Товар «Название» передан администратору на дополнительную проверку.
```

### Нужны исправления

```text
Для товара «Название» нужны исправления: [комментарий].
```

### Отклонение

```text
Товар «Название» не может быть опубликован: [причина].
```

Не отправлять продавцу:

- текст исключения;
- HTTP-код;
- название провайдера;
- сообщение API;
- информацию о лимитах Gemini.

## 11. Тексты интерфейса

Использовать единый словарь:

| Внутренний статус | Текст продавцу |
|---|---|
| `draft` | Черновик |
| `pending` | Ожидает проверки |
| `processing` | Проверяется |
| `needs_review` | На проверке у администратора |
| `changes_required` | Нужны исправления |
| `rejected` | Не может быть опубликован |
| `approved` | Одобрен |

Не использовать одновременно варианты:

- «Нужна ручная проверка»;
- «На ручной проверке»;
- «Передан на ручную проверку».

Основной вариант:

```text
На проверке у администратора
```

## 12. Этапы реализации

### Этап 1. Разделение публикации и намерения

1. Добавить `publication_requested`.
2. Выполнить миграцию данных.
3. Обновить модель и factory.
4. Обновить создание и редактирование.
5. Обновить сервис одобрения.

### Этап 2. Упрощение технических состояний

1. Переводить исчерпанные ошибки в `needs_review`.
2. Перенести существующие `failed`.
3. Убрать `failed` из интерфейса продавца.
4. Ограничить повтор ИИ административным интерфейсом.

### Этап 3. Единый UX состояния

1. Обновить `ProductViewStateFactory`.
2. Определить одно основное действие для каждого состояния.
3. Убрать недоступные кнопки.
4. Унифицировать тексты списка и карточки.

### Этап 4. Filament

1. Переименовать действия одобрения.
2. Показывать ожидаемый результат публикации.
3. Разделить пользовательский статус и технический журнал.
4. Проверить видимость действий для каждого статуса.

### Этап 5. Уведомления

1. Добавить уведомление автоматического одобрения.
2. Добавить уведомление передачи администратору.
3. Проверить ручные решения.
4. Исключить технические детали.

## 13. Обязательные тесты

### Матрица состояний продавца

Для каждого статуса проверить:

- текст статуса;
- текст публикации;
- пояснение;
- основную кнопку;
- пункты меню `⋮`;
- отсутствие запрещённых действий.

### Публикация

1. Отправка с `publication_requested=true`.
2. Автоматическое одобрение публикует товар.
3. Ручное одобрение публикует товар.
4. Одобрение с `publication_requested=false` оставляет товар скрытым.

### Ошибки провайдера

1. Временная ошибка оставляет товар в обработке.
2. Повторы выполняются автоматически.
3. После исчерпания попыток товар получает `needs_review`.
4. Продавец не видит техническую ошибку.
5. Администратор видит ошибку в журнале.

### Редактирование

1. Изменение контента снимает товар с публикации.
2. Версия модерации увеличивается.
3. Выбор отправки запускает новую проверку.
4. Сохранение черновика не запускает проверку.

### Уведомления

Проверить автоматическое одобрение, ручную проверку, доработку и отклонение.

## 14. Критерии завершения

Работа завершена, если:

- `is_active` означает только реальную публикацию;
- намерение хранится отдельно;
- результат одобрения предсказуем;
- технические ошибки не показываются продавцу;
- `failed` не является пользовательским состоянием;
- в каждом статусе есть не более одного основного действия;
- тексты одинаковы в списке, карточке и уведомлениях;
- Filament позволяет завершить любой ручной сценарий;
- полный набор тестов проходит без ошибок.
