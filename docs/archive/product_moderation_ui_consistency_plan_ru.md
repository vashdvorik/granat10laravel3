# Архив: план устранения ошибок интерфейса и логики модерации товаров

## 1. Цель

Привести кабинет продавца, Filament, уведомления и серверные действия к единой системе состояний товара.

Пользователь должен всегда понимать:

- опубликован ли товар на сайте;
- проходит ли он модерацию;
- требуется ли действие продавца;
- какая кнопка доступна сейчас;
- почему действие недоступно;
- что произойдёт после нажатия кнопки.

Главное правило: интерфейс не должен самостоятельно вычислять бизнес-логику через разрозненные проверки `is_active`, `display_status` и `moderation_status`.

## 2. Обнаруженные системные проблемы

### 2.1. Смешаны два разных понятия

Сейчас `is_active` используется одновременно как:

- намерение продавца опубликовать товар;
- фактическая публикация товара;
- условие для кнопок;
- условие тарифных лимитов.

При этом реальная видимость товара требует одновременно:

```text
is_active = true
moderation_status = approved
moderated_version = moderation_version
у продавца есть активный тариф
```

Из-за этого надпись «Опубликован» может не соответствовать реальной видимости товара.

### 2.2. Формы создания и редактирования вводят продавца в заблуждение

В формах поле `is_active` называется «Статус активности», а варианты называются:

- «Опубликован»;
- «Снят с публикации».

На этапе создания товар ещё не может быть опубликован: сначала он проходит локальную и ИИ-модерацию. Фактически переключатель означает намерение:

- «Сохранить и отправить на модерацию»;
- «Сохранить как черновик».

### 2.3. Карточка товара показывает неправильную кнопку

В `resources/views/backend/cabinet/products/show.blade.php` для любого товара с `is_active=false` показывается кнопка «Опубликовать».

Это неверно для состояний:

- `draft`;
- `pending`;
- `processing`;
- `needs_review`;
- `changes_required`;
- `rejected`;
- `failed`.

Сервис затем запрещает действие, но интерфейс не должен предлагать заведомо недоступную кнопку.

### 2.4. Список и детальная страница используют разные правила

Список товаров частично учитывает `moderation_status`, а детальная страница во многих местах проверяет только `is_active`.

Один товар может одновременно отображаться:

- в списке как «На проверке»;
- на детальной странице как «Опубликован»;
- отдельным бейджем как «Снят с публикации».

### 2.5. Filament показывает действия по неполным условиям

Обнаружены примеры:

- «Опубликовать» видна для любого `is_active=false`, даже если товар не одобрен;
- «Поднять» не имеет явного условия видимости только для опубликованного товара;
- ссылка «Открыть» показывается даже когда публичная страница товара недоступна;
- переключатель `is_active` в форме администратора выглядит как прямое управление публикацией, хотя модерация может это запретить;
- ручные решения доступны для `processing`, пока фоновая задача ещё может изменить тот же товар.

### 2.6. Политики проверяют владельца, но не состояние

`ProductPolicy` разрешает владельцу `activate`, `deactivate`, `submitForModeration` и `pushUp` без проверки допустимости перехода.

Фактическая проверка частично выполняется в сервисах. Это создаёт расхождение:

- кнопка отображается;
- policy разрешает запрос;
- сервис возвращает ошибку.

### 2.7. Статус `failed` имеет неоднозначное действие

Для `failed` одновременно существуют:

- повторная отправка товара продавцом через общий `submit`;
- отдельный retry-сервис в Filament;
- автоматическая команда повторной обработки.

Не определено, должен ли продавец:

- повторить проверку без изменения карточки;
- сначала редактировать товар;
- повторно отправить весь процесс модерации.

### 2.8. `rejected` разрешён к повторной отправке без изменений

Интерфейс показывает «Отправить на проверку» для `rejected`. Если товар запрещён принципиально, простая повторная отправка без новой версии создаёт бессмысленный цикл.

Следует определить:

- `changes_required` — можно исправить и отправить повторно;
- `rejected` — повторная отправка только после изменения модерируемого содержимого или решения администратора.

### 2.9. Изменение изображений сбрасывает модерацию без понятного сообщения

Удаление изображения и смена главного изображения вызывают `invalidate()` и переводят товар в `draft`.

Пользователь получает сообщение только об изображении, но не узнаёт:

- что одобрение отменено;
- что товар снят с публикации;
- что его нужно повторно отправить на проверку.

### 2.10. Сообщение «Товар создан» недостаточно точное

После создания возможны разные результаты:

- сохранён черновик;
- отправлен на модерацию;
- поставлен в очередь;
- автоматически одобрен;
- отправлен на ручную проверку;
- проверка временно завершилась ошибкой.

Сейчас контроллер обычно сообщает только «Товар создан».

### 2.11. Уведомления используют вычисляемый `display_status`

Уведомление сохраняет `display_status`, который смешивает модерацию и публикацию.

Например, после одобрения неактивного товара продавец может получить «Снят с публикации» вместо понятного «Товар одобрен. Теперь его можно опубликовать».

### 2.12. Терминология не унифицирована

Одновременно используются:

- «На проверке»;
- «Проверяется»;
- «Нужна ручная проверка»;
- «Отправить на проверку»;
- «Отправить на модерацию»;
- «Активен»;
- «Опубликован»;
- «Стоп»;
- «Снят с публикации».

Нужен единый словарь для продавца и отдельный технический словарь для администратора.

## 3. Целевая модель интерфейса

Следует разделить:

1. **Статус модерации** — `moderation_status`.
2. **Статус публикации** — вычисляемое состояние, а не прямое отображение `is_active`.
3. **Доступные действия** — вычисляются централизованно.
4. **Причина недоступности** — доступна интерфейсу как текст.

## 4. Целевая матрица состояний продавца

| Статус | Что показывать продавцу | Основная кнопка | Дополнительные действия |
|---|---|---|---|
| `draft` | Черновик. Товар не отправлен на проверку | «Отправить на модерацию» | Редактировать, удалить |
| `pending` | Ожидает автоматической проверки | Кнопок публикации нет | Просмотр, удалить при подтверждении |
| `processing` | Идёт автоматическая проверка | Кнопок действий нет | Просмотр |
| `needs_review` | Передан администратору на ручную проверку | Кнопок публикации нет | Просмотр |
| `changes_required` | Требуются исправления. Показать комментарий | «Исправить товар» | Удалить |
| `rejected` | Товар отклонён. Показать причину | «Редактировать» или обращение в поддержку | Удалить |
| `failed` | Проверка временно не выполнена | «Повторить проверку» | Редактировать, удалить |
| `approved`, `is_active=false` | Одобрен, но не опубликован | «Опубликовать» | Редактировать, удалить |
| `approved`, `is_active=true` | Опубликован | «Снять с публикации» | Поднять, редактировать, удалить |

Дополнительное условие: если нет активного тарифа или исчерпан лимит, вместо рабочей кнопки публикации показывать причину и ссылку на тарифы.

## 5. Целевая матрица действий администратора

| Состояние | Одобрить | На доработку | Отклонить | Повторить ИИ | Опубликовать | Снять | Поднять | Открыть публично |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `draft` | Нет | Нет | Нет | Нет | Нет | Нет | Нет | Нет |
| `pending` | Да | Да | Да | Нет | Нет | Нет | Нет | Нет |
| `processing` | Нет до завершения job | Нет | Нет | Нет | Нет | Нет | Нет | Нет |
| `needs_review` | Да | Да | Да | Нет | Нет | Нет | Нет | Нет |
| `changes_required` | Нет | Нет | Нет | Нет | Нет | Нет | Нет | Нет |
| `rejected` | По отдельному действию пересмотра | Нет | Нет | Нет | Нет | Нет | Нет | Нет |
| `failed` | Нет | Нет | Нет | Да | Нет | Нет | Нет | Нет |
| `approved`, выключен | Нет | Нет | Нет | Нет | Да | Нет | Нет | Нет |
| `approved`, включён | Нет | Нет | Нет | Нет | Нет | Да | Да | Да |

## 6. Архитектурное решение

### 6.1. Создать единый объект представления состояния

Добавить сервис или DTO, например:

```php
ProductModerationViewState
```

Он должен возвращать:

```text
status_label
status_description
status_color
is_public
can_submit
can_retry
can_publish
can_unpublish
can_push_up
can_edit
can_delete
can_open_public_page
disabled_reason
primary_action
```

Blade и Filament должны использовать этот объект вместо собственных `if`.

### 6.2. Создать единый сервис допустимых переходов

Например:

```php
ProductStateTransitionService
```

Методы:

```text
canSubmitForModeration()
canRetryModeration()
canApprove()
canRequestChanges()
canReject()
canPublish()
canUnpublish()
canPushUp()
```

Эти же методы должны использовать:

- policies;
- сервисы;
- Blade;
- Filament;
- API/AJAX-контроллеры.

### 6.3. Не хранить пользовательскую логику в `display_status`

`display_status` следует заменить или сузить:

- `moderation_status_label`;
- `publication_status_label`;
- `is_publicly_visible`.

Нельзя возвращать одним полем одновременно «Одобрен», «Опубликован» и «Снят с публикации».

## 7. Последовательность исправления

### Этап 1. Зафиксировать конечный автомат состояний

1. Утвердить матрицы из разделов 4 и 5.
2. Описать разрешённые переходы.
3. Запретить переходы, которых нет в матрице.
4. Отдельно определить поведение `rejected` и `failed`.

Результат: один документ является источником истины для разработки и тестов.

### Этап 2. Централизовать проверки действий

1. Создать `ProductStateTransitionService`.
2. Перенести туда проверки статуса, версии, активности и лимитов.
3. Обновить `ProductPolicy`.
4. Оставить повторную проверку внутри сервисов как защиту от прямого HTTP-запроса.
5. Добавить понятные причины запрета каждого действия.

Результат: кнопка, policy и сервис принимают одинаковое решение.

### Этап 3. Создать единое представление статуса

1. Создать `ProductModerationViewState`.
2. Разделить статус модерации и статус публикации.
3. Добавить единые подписи, цвета, описания и основное действие.
4. Удалить сравнения строк вида:

```php
$product->display_status === 'Опубликован'
```

Результат: тексты не влияют на бизнес-логику.

### Этап 4. Исправить формы создания и редактирования

Форма создания:

- заменить «Статус активности»;
- варианты: «Сохранить и отправить на модерацию» и «Сохранить как черновик»;
- по умолчанию можно оставить отправку на модерацию, но явно объяснить процесс;
- кнопка сохранения должна соответствовать выбранному действию.

Форма редактирования:

- убрать прямой выбор «Опубликован» для неодобренного товара;
- показывать текущий статус отдельным информационным блоком;
- предупреждать, что изменение модерируемых данных снимет товар с публикации и потребует новой проверки;
- для `changes_required` показывать комментарий администратора над формой.

### Этап 5. Исправить список товаров продавца

1. Использовать единый компонент статуса.
2. Убрать второй противоречащий бейдж.
3. Показывать только допустимые кнопки.
4. Для `pending`, `processing`, `needs_review` показывать ожидание без кнопки публикации.
5. Для `failed` показывать отдельную кнопку повтора.
6. Для `changes_required` вести сразу на редактирование.
7. Для `rejected` не разрешать слепую повторную отправку.
8. «Поднять» показывать только для реально видимого товара.

### Этап 6. Исправить детальную страницу продавца

1. Применить те же правила, что в списке.
2. Удалить проверку кнопок только по `is_active`.
3. Сделать единый блок:
   - статус;
   - объяснение;
   - комментарий;
   - следующее действие.
4. Историю модерации переводить в понятные пользовательские события.

### Этап 7. Исправить Filament

1. Убрать прямой toggle `is_active` из основной формы либо сделать его read-only.
2. Управлять публикацией только отдельными actions.
3. Скрывать «Опубликовать», пока версия не одобрена.
4. Скрывать «Поднять», если товар фактически не виден.
5. Скрывать публичную ссылку для невидимого товара.
6. Не разрешать ручное решение в статусе `processing`, пока job не завершён.
7. Добавить фильтры:
   - ожидают ИИ;
   - ожидают администратора;
   - требуют исправлений;
   - ошибки провайдера;
   - одобрены, но выключены;
   - опубликованы.
8. В таблице показывать отдельно:
   - модерацию;
   - публикацию;
   - доступность по тарифу.

### Этап 8. Исправить сообщения и уведомления

Создать единый каталог пользовательских сообщений.

Примеры:

- «Товар сохранён как черновик».
- «Товар сохранён и поставлен в очередь на проверку».
- «Автоматическая проверка завершена. Товар передан администратору».
- «Товар одобрен и опубликован».
- «Товар одобрен. Нажмите “Опубликовать”».
- «Проверка временно недоступна. Товар сохранён, повтор будет выполнен автоматически».
- «После изменения изображения товар снят с публикации и требует повторной модерации».

Уведомления должны хранить:

```text
event
moderation_status
publication_status
title
message
action_label
url
```

Не следует сохранять `display_status` как единственное объяснение события.

### Этап 9. Обработать редактирование опубликованного товара

1. До сохранения показать предупреждение.
2. При изменении названия, описания, категории, характеристик или изображений:
   - увеличить версию;
   - снять публикацию;
   - перевести в `draft`;
   - сообщить пользователю причину.
3. Изменения, не влияющие на модерацию, определить отдельно.
4. Смена главного изображения также должна иметь явное сообщение о повторной проверке либо не сбрасывать модерацию, если это допустимо политикой.

### Этап 10. Удалить дублирование Blade-разметки

Создать компоненты:

```text
components.product-moderation-status
components.product-publication-status
components.product-actions
components.product-moderation-message
```

Использовать их в:

- списке товаров;
- детальной странице;
- форме редактирования;
- виджетах кабинета.

## 8. Обязательные тесты

### 8.1. Матрица переходов

Для каждого статуса проверить:

- разрешённые действия;
- запрещённые действия;
- причину запрета;
- итоговый статус;
- значение `is_active`;
- изменение версии.

### 8.2. Тесты интерфейса продавца

Для каждого состояния проверить наличие и отсутствие:

- «Отправить на модерацию»;
- «Повторить проверку»;
- «Исправить товар»;
- «Опубликовать»;
- «Снять с публикации»;
- «Поднять»;
- публичной ссылки.

Проверять отдельно список и детальную страницу.

### 8.3. Тесты Filament

Для каждого состояния проверить видимость actions.

Особенно:

- `processing` не допускает ручного решения;
- `failed` показывает только retry;
- `approved + inactive` показывает publish;
- `approved + active` показывает unpublish и push;
- остальные статусы не показывают publish.

### 8.4. Тесты сообщений

Проверить сообщения после:

- создания черновика;
- создания с отправкой;
- успешного auto-approve;
- передачи на ручную проверку;
- требования исправлений;
- отклонения;
- ошибки Gemini;
- повторной проверки;
- изменения изображения;
- снятия и повторной публикации.

### 8.5. Тесты прямых запросов

Даже если кнопка скрыта, прямой HTTP-запрос должен вернуть `403` или `422` и не менять товар.

## 9. Порядок реализации без риска

1. Добавить тесты текущих противоречий.
2. Создать transition service.
3. Создать view-state DTO.
4. Обновить policies и сервисы.
5. Исправить формы.
6. Исправить список продавца.
7. Исправить детальную страницу.
8. Исправить Filament.
9. Унифицировать уведомления.
10. Удалить старые проверки и `display_status`.
11. Запустить полный PHPUnit.
12. Провести ручной acceptance-тест всех состояний.

## 10. Приоритет найденных проблем

### Критический

- неправильная кнопка «Опубликовать» на детальной странице;
- возможность действий Filament по одному `is_active`;
- форма создания сообщает «Опубликован» до модерации;
- разные правила списка и детальной страницы;
- ручное решение во время `processing`.

### Высокий

- повторная отправка `rejected` без изменения;
- неоднозначная обработка `failed`;
- изменение изображения молча сбрасывает модерацию;
- публичная ссылка и «Поднять» для невидимого товара;
- policies не учитывают автомат состояний.

### Средний

- неточные flash-сообщения;
- уведомления на основе `display_status`;
- дублирование Blade;
- неодинаковая терминология;
- отсутствие объяснения недоступных действий.

## 11. Критерии завершения

Работа считается завершённой, когда:

- для каждого статуса существует одна утверждённая комбинация кнопок;
- список, детальная страница и Filament показывают одинаковое состояние;
- тексты не участвуют в логических сравнениях;
- `is_active` не отображается продавцу как самостоятельный статус модерации;
- прямой запрос не обходит ограничения интерфейса;
- все переходы покрыты тестами;
- продавец всегда видит причину и следующее допустимое действие;
- полный набор тестов проходит без ошибок.
