# Архив: план внедрения ИИ-модерации изображений товаров

## Статус внедрения

На текущем этапе уже реализовано:

- отдельный `ProductImageModerationClient`;
- отдельный prompt для проверки изображений;
- Google/Gemini-клиент для отправки фото в vision-модель;
- `ModerateProductImagesJob` для фоновой проверки изображений;
- запись результата фото-модерации в `product_moderation_runs` с provider `image_google`;
- ожидание результата фото-модерации перед автопубликацией товара;
- блок настроек `Модерация изображений` в Filament;
- сохранение переменных `AI_IMAGE_MODERATION_*` через админку;
- показ проблемного фото продавцу;
- действия администратора для повтора проверки фото и запроса замены фото;
- фильтр и индикатор проблем с фото в Filament;
- подробный просмотр результата проверки фото в Filament;
- блок готовности проверки фото на странице настроек модерации;
- защита от показа старых причин после замены или удаления фото;
- сквозной тест сценария `text allow -> image review -> продавец видит проблему фото`;
- тесты на клиента, job, связку text+image и Filament-настройки.

Что ещё не завершено:

- боевое включение через `.env` и проверка на реальном API-ключе.

## Цель

Добавить отдельную модерацию фотографий товаров, чтобы товар автоматически публиковался только после успешной проверки текста и изображений.

Текущая текстовая модерация остаётся отдельным контуром. Изображения нельзя смешивать с текстовой проверкой DeepSeek, потому что текущая модель работает как текстовая и не должна получать `image_url`.

## Что должна проверять модерация изображений

Проверяем только правила безопасности площадки:

- запрещённые товары на фото: оружие, наркотики, опасные вещества, поддельные документы, деньги;
- откровенный, порнографический или интимный контент;
- экстремистские, оскорбительные, насильственные изображения;
- фото, явно не относящееся к товару;
- пустые, битые, бессмысленные изображения или заглушки;
- контактные данные, водяные знаки с телефонами/мессенджерами, если они нарушают правила площадки.

Не проверяем:

- оригинальность бренда;
- наличие сертификатов;
- точную модель товара;
- технические характеристики;
- качество фотографии как рекламного материала;
- юридическую корректность документов, если нет явного запрещённого контента.

## Целевая логика

### 1. Продавец сохраняет черновик

- Фото можно загрузить или не загружать.
- ИИ-модерация не запускается.
- Товар остаётся в статусе `draft`.

### 2. Продавец нажимает `Сохранить и отправить`

Система проверяет:

1. Есть ли хотя бы одно фото.
2. Прошла ли локальная проверка текста.
3. Запускает текстовую ИИ-модерацию.
4. Запускает ИИ-модерацию изображений.

### 3. Автоматическая публикация

Товар публикуется автоматически только если:

- локальная проверка прошла;
- текстовая ИИ-модерация вернула `allow`;
- image moderation вернула `allow`;
- риск не выше порога автопубликации;
- категория не исключена из автопубликации.

### 4. Если проблема в тексте

Статус товара:

- `Нужно редактировать`, если ИИ дал понятную причину;
- `На ручной проверке`, если нужна проверка администратора.

Продавцу показываем:

- поле, где проблема;
- что именно не так;
- что нужно исправить.

### 5. Если проблема на фото

Статус товара:

- `Нужно редактировать`, если фото нужно заменить/удалить;
- `На ручной проверке`, если ИИ не уверен.

Продавцу показываем:

- какое фото вызвало проблему;
- причину;
- рекомендацию: заменить фото, удалить фото или загрузить другое.

## Архитектура

### Новые сущности

#### `ProductImageModerationResult`

DTO результата проверки изображений:

- `decision`: `allow`, `review`, `block`;
- `riskScore`;
- `violations`;
- `sellerMessage`;
- `providerRequestId`;
- `imagesAnalyzed`;
- `imageResults`.

#### `ProductImageModerationClient`

Контракт клиента:

```php
interface ProductImageModerationClient
{
    public function moderate(ProductModerationPayload $payload): ProductImageModerationResult;
}
```

#### `ProductImageModerationPrompt`

Отдельный prompt только для изображений.

Нельзя использовать текстовый prompt, потому что правила похожи, но формат evidence должен ссылаться на конкретное изображение.

#### `ModerateProductImagesJob`

Отдельная очередь для фото:

- получает `product_id`;
- получает `content_version`;
- проверяет только актуальную версию товара;
- пишет отдельный moderation run;
- не блокирует основной request продавца.

## База данных

Есть два варианта.

### Вариант A — использовать текущую `product_moderation_runs`

Добавить новые значения:

- `provider = image_google` или `image_openai_compatible`;
- `trigger = image_queue`;
- `image_result` хранит детальный результат по каждому фото.

Плюсы:

- меньше миграций;
- проще внедрить быстро.

Минусы:

- таблица станет хранить разные типы проверок.

### Вариант B — отдельная таблица `product_image_moderation_runs`

Поля:

- `id`;
- `product_id`;
- `content_version`;
- `provider`;
- `model`;
- `status`;
- `decision`;
- `risk_score`;
- `image_results`;
- `error_code`;
- `error_message`;
- `provider_request_id`;
- `latency_ms`;
- `started_at`;
- `finished_at`;
- timestamps.

Рекомендация: начать с варианта A, потому что текущая система уже использует `product_moderation_runs`.

## Конфигурация

Добавить в `.env`:

```env
AI_IMAGE_MODERATION_ENABLED=true
AI_IMAGE_MODERATION_PROVIDER=google
AI_IMAGE_MODERATION_MODEL=gemini-2.5-flash
AI_IMAGE_MODERATION_BASE_URL=https://generativelanguage.googleapis.com/v1beta
AI_IMAGE_MODERATION_API_KEY=
AI_IMAGE_MODERATION_QUEUE=moderation
AI_IMAGE_MODERATION_MAX_IMAGES=5
AI_IMAGE_MODERATION_MAX_IMAGE_BYTES=2000000
AI_IMAGE_MODERATION_TIMEOUT=60
AI_IMAGE_MODERATION_RETRY_TIMES=2
AI_IMAGE_MODERATION_REQUESTS_PER_MINUTE=5
```

Важно: текстовый DeepSeek не трогаем.

## Filament-настройки

В странице настроек модерации добавить отдельный блок `Модерация изображений`:

- включить/выключить проверку фото;
- провайдер;
- модель;
- base URL;
- API key;
- лимит фото;
- лимит размера фото;
- таймаут;
- лимит запросов в минуту;
- режим автопубликации: требовать image moderation или отправлять на ручную проверку при недоступности.

## State machine

Нужно не плодить новые публичные статусы, а расширить внутреннюю логику.

Публичные статусы для продавца:

- `Черновик`;
- `Проверяется`;
- `Одобрен`;
- `Нужно редактировать`;
- `На ручной проверке`;
- `Отклонён`.

Внутренние этапы:

- `local_check`;
- `text_ai_check`;
- `image_ai_check`;
- `auto_decision`.

Если текст прошёл, а изображения нет:

- товар остаётся `processing`, пока работает image job;
- если image job вернул проблему — `changes_required`;
- если image job упал технически — `needs_review` или повторная попытка, в зависимости от retry policy.

## UX для продавца

### В карточке товара

Показывать не общий текст “товар передан на проверку”, а конкретику:

- `Модерация: Нужно редактировать`;
- блок `Что нужно исправить`;
- для фото:
  - миниатюра проблемного изображения;
  - причина;
  - кнопка/ссылка `Заменить фото`.

### На форме редактирования

Возле блока фото:

- показать проблему конкретного изображения;
- подсветить фото;
- дать рекомендацию: `Удалите это фото или загрузите другое`.

### На списке товаров

Не перегружать карточку:

- показывать только статус;
- детальные причины — внутри карточки товара.

## Админка Filament

В `ProductResource` добавить:

- колонку `Фото проверены`;
- фильтр `Проблемы с фото`;
- action `Одобрить фото`;
- action `Запросить замену фото`;
- action `Повторить проверку фото`;
- блок просмотра image moderation result.

Администратор должен видеть:

- какое изображение вызвало проблему;
- ответ ИИ;
- risk score;
- provider/model/request id;
- историю попыток.

## Очередь

Команда worker:

```bash
php artisan queue:work --queue=moderation --tries=3 --timeout=90
```

Если нагрузка вырастет, лучше разделить очереди:

```bash
php artisan queue:work --queue=moderation-text --tries=3 --timeout=90
php artisan queue:work --queue=moderation-images --tries=3 --timeout=90
```

На первом этапе можно оставить одну очередь `moderation`.

## Обработка ошибок

Если image provider недоступен:

- не показывать продавцу техническую ошибку;
- статус: `На ручной проверке`;
- сообщение продавцу: `Фото товара переданы администратору на проверку.`;
- в `product_moderation_runs` сохранить реальную ошибку API.

Если provider вернул неверный JSON:

- повторить по retry policy;
- после исчерпания попыток — `needs_review`;
- администратору показать причину в Filament.

Если фото слишком большое:

- не отправлять его в ИИ;
- попросить продавца загрузить фото меньшего размера или сжать на сервере.

## Этапы внедрения

### Этап 1. Подготовка архитектуры

- Добавить config для image moderation.
- Добавить DTO `ProductImageModerationResult`.
- Добавить контракт `ProductImageModerationClient`.
- Добавить prompt для изображений.
- Добавить feature flags.

### Этап 2. Провайдер изображений

- Реализовать `GoogleImageModerationClient`.
- Подготовить изображения через существующий `ProductModerationImagePreparer`.
- Ограничить размер и количество изображений.
- Валидировать JSON-ответ.

### Этап 3. Job и запись результата

- Добавить `ModerateProductImagesJob`.
- Писать результат в `product_moderation_runs`.
- Защититься от устаревшей `content_version`.
- Добавить retry/backoff/unique lock.

### Этап 4. Объединение решений

- Обновить `ProductAutoApprovalPolicy`.
- Автопубликовать только если текст и фото прошли.
- Если текст `allow`, фото `review` — статус `Нужно редактировать` или `На ручной проверке`.

### Этап 5. UI продавца

- Добавить отображение проблемных фото.
- Убрать дублирование сообщений.
- Добавить ссылку на блок фото в форме редактирования.
- Проверить мобильную версию.

### Этап 6. Filament

- Добавить настройки image moderation.
- Добавить просмотр результатов.
- Добавить действия администратора.

### Этап 7. Тесты

Покрыть:

- товар без фото нельзя отправить на публикацию;
- черновик без фото можно сохранить;
- текст прошёл, фото прошло — автопубликация;
- текст прошёл, фото не прошло — `changes_required`;
- image provider упал — `needs_review`;
- старая версия job не меняет товар;
- seller видит конкретную причину по фото;
- admin может вручную одобрить.

### Этап 8. Продакшен

- Проверить API key.
- Запустить queue worker.
- Настроить лимиты запросов.
- Настроить логирование.
- Проверить повторные попытки.
- Протестировать 10–20 реальных товаров с разными фото.

## Риски

- Vision API дороже текстового.
- Некоторые модели могут давать ложные срабатывания.
- Нельзя автоматически доверять ИИ при спорных изображениях.
- Нужно хранить понятный audit trail для администратора.

## Рекомендуемый MVP

Для первого релиза достаточно:

1. Google/Gemini image moderation.
2. Проверка до 5 фото.
3. Отдельный image prompt.
4. Запись результата в `product_moderation_runs`.
5. Автопубликация только при `text allow + image allow`.
6. Показ продавцу конкретной проблемы по фото.
7. Ручное одобрение в Filament.
