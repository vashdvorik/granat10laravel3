# Архив: аудит Laravel-проекта

Дата аудита: 04.06.2026

## 1. Краткий вывод

Проект является классическим Laravel-монолитом: маршруты, контроллеры, Eloquent-модели, Blade-шаблоны, Filament-админка и Fortify-авторизация. Архитектура рабочая, но сейчас она ближе к "толстые контроллеры + Active Record", чем к аккуратно разделенному Laravel-приложению.

Главная проблема не в выборе Laravel, а в распределении ответственности. Валидация, бизнес-правила, работа с файлами, транзакции, кеширование и подготовка представлений часто находятся в одних и тех же контроллерах или моделях. Это усложняет сопровождение, тестирование и развитие проекта.

## 2. Что уже сделано хорошо

- Используется стек Laravel 10, PHP 8.1+, PHPUnit, Laravel Pint, Fortify, Sanctum и Filament 3.
- Есть доменная модель: пользователи, продавцы, товары, категории, изображения, тарифные пакеты.
- Категории переведены на Nested Set через `kalnoy/nestedset`, что лучше обычной ручной рекурсии для дерева.
- Есть кеширование категорий, продавцов, диапазона цен и счетчиков товаров.
- Есть автоматическая очистка части кешей через события моделей.
- Есть тесты в `tests/Feature` и `tests/Unit`, включая тесты кеша, лимитов тарифов, scope-ов и job прогрева категорий.
- Для тарифных операций используются транзакции.
- Для админки подключен activity log и отдельный доступ через middleware.

## 3. Основные архитектурные проблемы

### 3.1. Слишком крупные контроллеры

Крупнейшие файлы:

- `app/Http/Controllers/Backend/ProductController.php` - около 697 строк.
- `app/Http/Controllers/CatalogController.php` - около 410 строк.
- `app/Http/Controllers/CabinetController.php` - около 249 строк.
- `app/Models/Seller.php` - около 474 строк.

В `Backend\ProductController` одновременно находятся:

- валидация товара;
- проверка прав владельца;
- проверка лимитов тарифа;
- проверка конечной категории;
- генерация alias;
- загрузка и обработка изображений;
- изменение статуса товара;
- удаление файлов;
- AJAX-ответы.

Это делает контроллер точкой риска: любое изменение товара может затронуть много несвязанных правил.

### 3.2. Бизнес-логика смешана с Eloquent-моделями

Модели `Seller`, `Product`, `Category`, `SellerPackage` содержат не только связи и scope, но и значительную доменную логику:

- проверка лимитов тарифа;
- автопродление пакета;
- расчет статуса пакета;
- очистка кешей;
- прогрев кеша;
- формирование пользовательских сообщений.

Это не ошибка для небольшого проекта, но при росте такой подход быстро приводит к перегрузке моделей. Особенно это заметно в `Seller`, где модель стала одновременно сущностью, сервисом тарифов и генератором UI-сообщений.

### 3.3. Нет слоя Form Request

Валидация выполняется прямо в контроллерах через `validate()` и `Validator::make()`. Из-за этого:

- правила повторяются в `store` и `update`;
- сложнее тестировать валидацию отдельно;
- контроллеры раздуваются;
- сложнее поддерживать локализованные сообщения.

Для Laravel правильнее вынести валидацию в `FormRequest` классы.

### 3.4. Нет сервисного слоя для ключевых сценариев

В проекте есть сложные сценарии, которые уже заслуживают отдельных сервисов:

- создание и обновление товара;
- обработка изображений товара;
- покупка тарифа;
- автопродление тарифа;
- проверка лимитов пакета;
- кеширование каталога и категорий;
- подсчет статистики кабинета.

Сейчас эти сценарии распределены между контроллерами и моделями.

### 3.5. Проблемный boot в `AppServiceProvider`

`AppServiceProvider` в `boot()` проверяет наличие таблицы `categories` и сразу обращается к базе, чтобы расшарить категории во views. Из-за этого консольные команды, включая `php artisan route:list` и `php artisan test`, могут падать, если MySQL недоступен.

Фактический результат проверки:

- `php artisan route:list` падает с `SQLSTATE[HY000] [2002]`.
- `php artisan test` падает с той же ошибкой до запуска тестов.

Для Laravel это плохой признак: route-list, config-cache, test, migrate и другие artisan-команды не должны зависеть от доступности production-БД на этапе загрузки приложения.

### 3.6. API почти отсутствует

`routes/api.php` содержит только стандартный `/user` под `auth:sanctum`. Основная логика сайта работает через web-маршруты и Blade. AJAX-эндпоинты возвращают HTML partials, а не JSON.

Это нормально для server-rendered сайта, но важно не считать проект API-first или SPA. Если в будущем появится мобильное приложение или отдельный frontend, API придется проектировать отдельно.

### 3.7. Админский доступ захардкожен по email

Статус на 08.06.2026: исправлено. `OnlyMyEmail` удалён, доступ переведён на Gate `access-admin` и application-owned permission `browse_admin`.

Middleware `OnlyMyEmail` содержит конкретный email в коде. Это простой быстрый способ, но для правильной разработки лучше использовать:

- application-owned роли и permissions;
- policy/gate;
- значение из config/env только как временную меру.

### 3.8. Есть временные и устаревшие файлы

В проекте найдены признаки технического долга:

- `app/Http/Controllers/CatalogController.php.old`;
- `database/seeders/CategoriesTableSeeder.php.old`;
- маршрут `/test-package-system` в `routes/web.php`;
- файл `test_cache.php` в корне;
- файл `LOGGG.txt`;
- файл с именем `prepareBindings($bindings)`.

Такие артефакты лучше удалить или перенести в отдельную архивную папку вне production-кода.

### 3.9. Кодировка комментариев повреждена

В ряде PHP-файлов комментарии отображаются как битая кодировка. Это мешает поддержке и ревью. Файлы проекта должны быть приведены к UTF-8 без BOM.

### 3.10. Дублирование кеш-логики

Кеши категорий, товаров, продавцов и меню очищаются из разных мест:

- `Product`;
- `Seller`;
- `Category`;
- `SellerPackage`;
- `WarmCategoriesCache`;
- `CatalogController`.

При изменении бизнес-правил есть риск забыть очистить один из связанных ключей. Лучше централизовать кеширование каталога.

## 4. Оценка по областям

### Архитектура

Оценка: средняя.

Основа правильная для Laravel: MVC, Eloquent, Blade, маршруты, middleware, jobs, console commands. Но границы ответственности размыты. Для дальнейшего роста нужен слой application services/actions и FormRequest.

### Безопасность

Оценка: средняя.

Положительно:

- есть `auth` middleware для кабинета;
- есть проверки владения товаром и магазином;
- есть транзакции при покупке тарифа;
- изображения валидируются по типу и размеру.

Риски:

- тестовый публичный маршрут `/test-package-system`;
- AJAX-эндпоинты возвращают HTML, важно постоянно проверять CSRF и авторизацию;
- часть проверок прав дублируется вручную вместо policies.

### Производительность

Оценка: средняя.

Положительно:

- есть кеш категорий и продавцов;
- есть Nested Set;
- есть eager loading в ряде запросов;
- есть отдельная job для прогрева кеша.

Риски:

- `AppServiceProvider` делает работу с БД при boot;
- в контроллерах есть рекурсивные подсчеты;
- `Product::getCachedPriceRange()` считает по всем товарам, а не только видимым;
- кеш-ключи и инвалидация распределены по проекту.

### Тестируемость

Оценка: ниже средней из-за boot-проблемы.

Тестовая база есть, но сейчас `php artisan test` не стартует из-за подключения к MySQL во время загрузки приложения. После исправления `AppServiceProvider` тесты станут главным инструментом безопасного рефакторинга.

### Поддерживаемость

Оценка: средняя-низкая.

Главные причины:

- крупные контроллеры;
- крупная модель `Seller`;
- бизнес-логика в UI-контроллерах;
- временные файлы в корне и коде;
- поврежденные комментарии;
- устаревшая документация частично не совпадает с текущим состоянием.

## 5. Рекомендуемое целевое состояние

Проект не нужно переписывать. Правильный путь - постепенный рефакторинг внутри Laravel:

- оставить Laravel MVC и Blade;
- сделать контроллеры тоньше;
- вынести валидацию в `FormRequest`;
- вынести сценарии в `app/Services` или `app/Actions`;
- вынести проверки доступа в `Policies`;
- централизовать кеш каталога;
- убрать запросы к БД из глобального boot;
- привести тесты к стабильному запуску;
- удалить временные маршруты и старые файлы;
- обновить документацию после каждого крупного этапа.
