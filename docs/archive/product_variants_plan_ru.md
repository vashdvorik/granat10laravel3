# Архив: план внедрения вариативных товаров — отменён

> **Статус: отменён 14.06.2026.**
>
> Проект сохраняет текущую модель: одна карточка товара имеет одну цену
> `products.price` и одну скидочную цену `products.lowprice`.
> Таблицы, сервисы и интерфейсы вариаций внедряться не будут.
> Документ сохранён только как архив ранее рассмотренного решения и не является
> частью активного плана разработки.

Дата составления: 09.06.2026.

## 1. Цель

Добавить товарам вариации, у каждой из которых могут быть собственные:

- значения характеристик: размер, цвет, объём, материал и другие;
- обычная цена;
- цена со скидкой;
- артикул;
- активность;
- порядок отображения;
- остаток — при последующем внедрении складского учёта;
- изображения — на отдельном этапе.

Пример:

| Товар | Вариация | Цена | Цена со скидкой |
|---|---|---:|---:|
| Футболка | Белая / S | 500 RUP | — |
| Футболка | Белая / M | 550 RUP | 500 RUP |
| Футболка | Чёрная / M | 600 RUP | — |

Товар остаётся одной карточкой и одним URL. Покупатель выбирает вариацию внутри карточки товара.

## 2. Текущее состояние проекта

Сейчас цена хранится непосредственно в таблице `products`:

- `products.price` — обычная цена;
- `products.lowprice` — цена со скидкой;
- `products.sale_started_at` — дата начала скидки.

Эти поля используются в:

- `Product`;
- `ProductRequest`;
- `ProductWriteService`;
- `CatalogPageService`;
- фильтрации каталога по цене;
- странице распродажи;
- карточках товаров;
- странице товара;
- кабинете продавца;
- Filament;
- статистике;
- кешировании диапазона цен;
- SEO и структурированных данных, если они будут расширяться;
- PHPUnit-тестах.

Поэтому нельзя просто перенести цену в новую таблицу и удалить поля из `products`: это нарушит текущую выдачу и существующие товары.

## 3. Основные решения

### 3.1. Вариация является дочерней сущностью товара

Предлагаемая связь:

```text
Product
  ├── ProductVariant
  │     ├── AttributeValue: Белый
  │     └── AttributeValue: M
  └── ProductVariant
        ├── AttributeValue: Чёрный
        └── AttributeValue: L
```

Один товар должен иметь минимум одну вариацию. Для обычного товара без выбора параметров создаётся одна базовая вариация.

### 3.2. Цена вариации — источник истины

После полного перехода:

- цена редактируется в `product_variants`;
- `products.price` и `products.lowprice` временно сохраняются как совместимые агрегированные поля;
- агрегированные поля автоматически синхронизируются с вариациями;
- старый код продолжает работать во время поэтапного перехода.

Рекомендуемое значение `products.price` — минимальная актуальная обычная цена активных вариаций.

Рекомендуемое значение `products.lowprice` — минимальная актуальная цена со скидкой активных вариаций или `null`.

Для корректного отображения диапазона следует добавить:

- `products.min_price`;
- `products.max_price`;
- `products.min_final_price`;
- `products.max_final_price`.

`final_price` — фактическая цена вариации: `lowprice`, если скидка задана, иначе `price`.

### 3.3. Один URL на товар

Не создавать отдельные публичные URL для каждой вариации.

Основной URL остаётся:

```text
/{location}/product/{product_alias}
```

Выбранную вариацию при необходимости можно передавать query-параметром:

```text
/{location}/product/tshirt-white?variant=125
```

Canonical должен указывать на URL товара без `variant`, чтобы не создавать SEO-дубли.

### 3.4. Атрибуты должны быть нормализованы

Не хранить строку вида `Белый / M` как единственный источник данных. Это затруднит проверку дублей, фильтрацию и развитие поиска.

Нужны отдельные справочники атрибутов и значений:

- атрибут `Цвет`;
- значения `Белый`, `Чёрный`;
- атрибут `Размер`;
- значения `S`, `M`, `L`.

## 4. Предлагаемая схема базы данных

### 4.1. `product_attributes`

Справочник характеристик, которые могут формировать вариации.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | Первичный ключ |
| `name` | string | Размер, Цвет, Объём |
| `slug` | string unique | `size`, `color`, `volume` |
| `type` | string | `select`, в будущем `color` |
| `is_active` | boolean | Доступность |
| `is_filterable` | boolean | Участие в фильтрах каталога |
| `sort_order` | integer | Очередность |
| timestamps | | |

### 4.2. `product_attribute_values`

Справочник значений атрибутов.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | Первичный ключ |
| `product_attribute_id` | FK | Атрибут |
| `value` | string | `Белый`, `M`, `500 мл` |
| `slug` | string | Системное значение |
| `color_hex` | nullable string | Цвет для визуального выбора |
| `sort_order` | integer | Очередность |
| `is_active` | boolean | Доступность |
| timestamps | | |

Ограничение:

```text
unique(product_attribute_id, slug)
```

### 4.3. `category_product_attribute`

Определяет, какие атрибуты доступны для конкретной категории.

| Поле | Тип |
|---|---|
| `category_id` | FK |
| `product_attribute_id` | FK |
| `is_required` | boolean |
| `sort_order` | integer |

Это не позволит показывать атрибут «Размер одежды» в категориях, где он не нужен.

На первом MVP-этапе связь с категориями можно использовать только в Filament, а кабинет продавца подключить после стабилизации модели.

### 4.4. `product_variants`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | bigint | Первичный ключ |
| `product_id` | FK cascade | Родительский товар |
| `sku` | nullable string | Артикул продавца |
| `price` | decimal(10,2) | Обычная цена |
| `lowprice` | nullable decimal(10,2) | Цена со скидкой |
| `sale_started_at` | nullable datetime | Начало скидки |
| `stock_quantity` | nullable unsigned integer | Остаток; `null` — склад не учитывается |
| `is_active` | boolean | Доступность вариации |
| `is_default` | boolean | Вариация по умолчанию |
| `sort_order` | integer | Очередность |
| timestamps | | |
| soft deletes | опционально | История и безопасное удаление |

Ограничения:

- цена не может быть отрицательной;
- `lowprice` должна быть меньше `price`;
- у товара должна быть только одна вариация по умолчанию;
- сочетание значений атрибутов внутри товара должно быть уникальным;
- SKU должен быть уникальным как минимум внутри одного магазина.

Для SKU рекомендуется составное бизнес-ограничение на уровне сервиса:

```text
seller_id + sku
```

Так как `seller_id` находится у товара, проверка выполняется валидатором и сервисом.

### 4.5. `product_variant_attribute_value`

Связывает вариацию со значениями атрибутов.

| Поле | Тип |
|---|---|
| `product_variant_id` | FK cascade |
| `product_attribute_value_id` | FK restrict |

Нельзя назначить вариации два значения одного атрибута.

### 4.6. Изображения вариаций

На первом этапе все вариации используют общие изображения товара.

На отдельном этапе в `images` можно добавить nullable:

```text
product_variant_id
```

Тогда изображение с `product_variant_id = null` является общим, а изображение с ID вариации относится к конкретному цвету или исполнению.

Не рекомендуется внедрять изображения вариаций одновременно с основной моделью цен: это существенно увеличит объём и риск первого этапа.

## 5. Доменные модели

Добавить:

- `ProductVariant`;
- `ProductAttribute`;
- `ProductAttributeValue`.

Связи:

```php
Product::variants()
Product::activeVariants()
Product::defaultVariant()
ProductVariant::product()
ProductVariant::attributeValues()
ProductAttribute::values()
ProductAttribute::categories()
ProductAttributeValue::attribute()
ProductAttributeValue::variants()
```

В `ProductVariant` нужны вычисляемые свойства:

- `final_price`;
- `has_discount`;
- `discount_percent`;
- `display_name`;
- `is_available`.

Ценовые вычисления нельзя дублировать в Blade.

## 6. Сервисный слой

### 6.1. `ProductVariantService`

Ответственность:

- создание и обновление вариаций;
- проверка уникальности комбинаций;
- назначение вариации по умолчанию;
- запрет удаления последней вариации;
- синхронизация агрегированных цен товара;
- установка `sale_started_at`;
- транзакционное сохранение;
- очистка связанных кешей;
- журналирование административных изменений.

### 6.2. `ProductPriceService`

Ответственность:

- расчёт обычной, минимальной и максимальной цены;
- расчёт фактической цены с учётом скидки;
- формирование текста:
  - `500 RUP`;
  - `от 500 RUP`;
  - `500–800 RUP`;
- вычисление максимального процента скидки для карточки;
- предоставление единых данных каталогу, странице товара и SEO.

### 6.3. Изменение `ProductWriteService`

На переходном этапе:

- создание товара и его первой вариации выполняется в одной транзакции;
- старые поля `price` и `lowprice` принимаются формой только до перевода интерфейса;
- после перевода формы сервис получает массив `variants`;
- товар не должен сохраняться частично, если вариации не прошли проверку.

## 7. Миграция существующих данных

Миграция должна быть обратимо-безопасной и выполняться поэтапно.

### Этап A. Создать новые таблицы

Добавить таблицы атрибутов и вариаций, не изменяя текущие поля товара.

### Этап B. Создать базовую вариацию каждому товару

Для каждого существующего товара создать одну вариацию:

```text
price = products.price
lowprice = products.lowprice
sale_started_at = products.sale_started_at
is_active = true
is_default = true
```

Такая вариация не обязана иметь значения атрибутов. Это нормальный простой товар.

Backfill должен быть:

- отдельной Artisan-командой или идемпотентным сидером;
- безопасным для повторного запуска;
- пакетным через `chunkById()`;
- с итоговым отчётом;
- покрыт тестом.

### Этап C. Проверить целостность

Перед переключением кода проверить:

- каждый товар имеет минимум одну вариацию;
- у каждого товара ровно одна вариация по умолчанию;
- цены совпадают с исходными полями;
- скидочные товары сохранили скидку и дату;
- количество товаров не изменилось;
- региональная видимость не изменилась;
- лимиты тарифов продолжают считать товары, а не вариации.

### Этап D. Перевести чтение

Карточки и страница товара начинают читать цены через `ProductPriceService`, но совместимые поля `products.price` остаются.

### Этап E. Перевести запись

Кабинет и Filament начинают создавать и редактировать вариации.

### Этап F. Удаление старых полей

Не выполнять сразу.

Удалять `products.price`, `products.lowprice` и `products.sale_started_at` можно только после:

- полного перевода запросов;
- обновления всех тестов;
- проверки production-данных;
- проверки импорта/сидеров;
- отдельного backup;
- периода стабильной работы.

Практичнее оставить агрегированные поля в `products` как денормализованный индекс для быстрого каталога.

## 8. Кабинет продавца

### 8.1. Создание товара

Форма должна поддерживать два режима:

1. **Простой товар** — одна вариация без атрибутов.
2. **Товар с вариантами** — продавец выбирает атрибуты и создаёт комбинации.

Рекомендуемый интерфейс:

1. заполнить общие данные товара;
2. выбрать атрибуты, например Цвет и Размер;
3. отметить доступные значения;
4. нажать «Создать комбинации»;
5. заполнить цену, скидку, SKU и активность каждой комбинации;
6. сохранить товар.

Пример таблицы:

| Вариация | SKU | Цена | Скидка | Активна |
|---|---|---:|---:|---|
| Белый / S | TS-W-S | 500 | — | Да |
| Белый / M | TS-W-M | 550 | 500 | Да |

### 8.2. Защита от ошибок

- предупреждать перед повторной генерацией комбинаций;
- не удалять заполненные вариации без подтверждения;
- не разрешать одинаковые комбинации;
- не разрешать удаление последней вариации;
- автоматически выбирать новую вариацию по умолчанию при отключении текущей;
- ограничить максимальное число вариаций одного товара, например 100;
- проверять владение товаром через `ProductPolicy`.

## 9. Filament

Добавить:

- управление справочником атрибутов;
- управление значениями атрибутов;
- назначение атрибутов категориям;
- repeater или relation manager вариаций в `ProductResource`;
- фильтр товаров без активных вариаций;
- колонки минимальной и максимальной цены;
- поиск по SKU;
- безопасные bulk-действия без массового удаления вариаций.

Для большого числа комбинаций предпочтителен `RelationManager`, а не тяжёлый вложенный `Repeater`.

## 10. Публичная карточка товара

Страница товара должна:

- загружать только активные вариации;
- отображать доступные атрибуты;
- не разрешать несуществующую комбинацию;
- менять цену без перезагрузки страницы;
- менять скидку и процент скидки;
- выбирать вариацию по умолчанию;
- сохранять доступность без обязательного JavaScript на уровне серверной разметки;
- при передаче `variant` проверять принадлежность вариации товару.

JavaScript получает безопасную JSON-структуру:

```json
{
  "variants": [
    {
      "id": 125,
      "values": {"color": "white", "size": "m"},
      "price": "550.00",
      "lowprice": "500.00",
      "available": true
    }
  ]
}
```

Не передавать в JSON служебные или административные поля.

## 11. Каталог, поиск и сортировка

### 11.1. Отображение цены

- одна цена у всех вариаций — показать обычную цену;
- разные цены — показать `от N RUP` или диапазон;
- скидка только у части вариаций — не показывать вводящий в заблуждение общий процент без уточнения;
- распродажа включает товар, если хотя бы одна активная вариация имеет действующую скидку.

### 11.2. Фильтрация по цене

Товар должен попадать в диапазон, если хотя бы одна активная вариация имеет `final_price` внутри диапазона.

Для производительности рекомендуется использовать агрегированные поля в `products`, но точная семантика должна быть определена заранее:

- фильтр по минимальной цене товара — быстро, но менее точно;
- `whereHas(activeVariants)` по цене — точно, но тяжелее;
- агрегированные min/max цены плюс индексы — рекомендуемый компромисс.

### 11.3. Сортировка

- по возрастанию — `min_final_price`;
- по убыванию — `max_final_price` либо `min_final_price`, решение должно быть единым;
- рекомендуемый вариант — сортировать по минимальной доступной цене.

### 11.4. Индексы

Добавить индексы:

```text
product_variants(product_id, is_active)
product_variants(product_id, sort_order)
product_variants(price)
product_variants(lowprice)
product_attribute_values(product_attribute_id, sort_order)
product_variant_attribute_value(product_variant_id)
product_variant_attribute_value(product_attribute_value_id)
products(min_final_price)
products(max_final_price)
```

## 12. Кеширование

Изменение вариации должно очищать:

- диапазон цен;
- меню пустых/непустых категорий;
- счётчики категории и родителей;
- кеш продавца;
- кеш карточки товара, если он будет добавлен;
- региональные варианты перечисленных ключей.

Добавить `ProductVariantObserver`, который вызывает централизованную инвалидацию через `CatalogCacheService`.

Не очищать весь cache store.

Синхронизацию агрегированных цен выполнять до инвалидации кэша и желательно после успешной транзакции.

## 13. Региональность

Вариация наследует регион от товара через продавца:

```text
ProductVariant → Product → Seller → Settlement
```

Отдельный `settlement_id` в вариации не нужен.

Все региональные правила продолжают применяться к товару:

- региональные URL;
- региональная фильтрация;
- sitemap;
- кеши;
- видимость магазина;
- активный тариф продавца.

## 14. SEO

### Карточка товара

- один canonical на товар;
- цена в structured data должна соответствовать активным вариациям;
- при разных ценах использовать `AggregateOffer`;
- `lowPrice` — минимальная фактическая цена;
- `highPrice` — максимальная фактическая цена;
- `offerCount` — число активных доступных вариаций;
- SKU отдельной вариации можно передавать в `Offer`;
- отключённые вариации не должны попадать в structured data.

### Каталог

Title и Description товара не должны автоматически включать название конкретной вариации, если URL общий.

Query-параметр `variant`:

- не включается в canonical;
- не создаёт отдельную sitemap-запись;
- не должен индексироваться как отдельная страница.

## 15. Сиды и фабрики

Обновить:

- `ProductFactory`;
- `ProductsTableSeeder`;
- тестовые сценарии Filament;
- демонстрационные товары.

Каждый создаваемый в тестах товар должен автоматически получать базовую вариацию либо фабрика должна предоставлять состояния:

```php
Product::factory()->withDefaultVariant()
Product::factory()->withVariants()
ProductVariant::factory()->discounted()
```

Не рекомендуется создавать вариацию из model event `Product::created`: это усложнит импорт и может создавать неожиданные записи. Явное создание через сервис или фабрику безопаснее.

## 16. Тестирование

После каждого этапа запускать профильные тесты, затем полный PHPUnit.

### Unit

- расчёт `final_price`;
- расчёт диапазона;
- скидка и процент;
- формирование названия вариации;
- уникальность комбинации;
- выбор вариации по умолчанию;
- синхронизация агрегированных цен.

### Feature

- создание простого товара;
- создание товара с несколькими вариациями;
- обновление цен;
- запрет неверной скидки;
- запрет одинаковых комбинаций;
- запрет чужому продавцу;
- удаление вариации;
- запрет удаления последней вариации;
- отключение вариации по умолчанию;
- rollback при ошибке одной вариации.

### Каталог

- минимальная цена отображается правильно;
- диапазон отображается правильно;
- ценовой фильтр учитывает вариации;
- распродажа учитывает скидку вариации;
- поиск не дублирует один товар по числу вариаций;
- пагинация считает товары, а не вариации;
- региональная фильтрация сохраняется;
- AJAX выдаёт те же цены, что обычная страница.

### Страница товара

- активные вариации доступны;
- неактивные скрыты;
- цена меняется при выборе;
- неизвестный `variant` не раскрывает чужую вариацию;
- вариант другого товара отклоняется;
- canonical не содержит параметр вариации.

### Filament

- администратор управляет атрибутами;
- значения атрибутов нельзя удалить при использовании без безопасной обработки;
- вариации редактируются;
- SKU ищется;
- права доступа соблюдаются.

### Миграция

- backfill идемпотентен;
- каждому старому товару создана одна вариация;
- цены и скидки сохранены;
- повторный запуск не создаёт дубли;
- количество товаров не меняется.

## 18. Что не следует делать

- не хранить все вариации одним JSON-полем в `products`;
- не создавать отдельный товар на каждый размер или цвет;
- не удалять старые цены до завершения перехода;
- не объединять схему, кабинет, Filament, изображения и SEO в один большой этап;
- не считать вариации в тарифном лимите как отдельные товары;
- не дублировать товар в каталоге по числу вариаций;
- не доверять цене, присланной JavaScript;
- не разрешать изменение вариаций без проверки владельца товара;
- не очищать весь кеш после изменения одной вариации.

## 19. Оценка масштаба

Это крупная доменная задача, потому что цена товара сейчас используется практически во всех слоях проекта.

Ориентировочно:

- схема, модели, сервисы и backfill: 2–3 рабочих дня;
- каталог, фильтры, кеши и страница товара: 2–4 дня;
- Filament и кабинет продавца: 3–5 дней;
- SEO, тесты, проверка и стабилизация: 2–3 дня;
- изображения вариаций: дополнительно 2–4 дня.

Базовая качественная версия без складского учёта и отдельных изображений: примерно 9–15 рабочих дней при последовательной реализации и тестировании.

## 20. Рекомендуемый MVP

Для первой версии включить:

- простой товар как одну вариацию;
- атрибуты и значения;
- несколько вариаций;
- отдельную цену и скидку;
- SKU;
- активность;
- одну вариацию по умолчанию;
- выбор вариации на странице товара;
- минимальную цену в каталоге;
- корректные фильтры, кеши и SEO;
- управление через Filament и кабинет продавца.

Отложить:

- отдельные изображения вариаций;
- складские резервы;
- заказы и корзину, если их пока нет в проекте;
- импорт вариаций из Excel;
- массовое изменение остатков;
- сложные цветовые галереи.

Такой порядок сохраняет текущую логику проекта, позволяет безопасно перенести существующие товары и не блокирует дальнейшее развитие магазина.
